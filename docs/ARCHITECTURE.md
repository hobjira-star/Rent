# ข้อกำหนดทางเทคนิค (Rent)

> เอกสารสำหรับนักพัฒนา คู่กับ [PLAN.md](./PLAN.md) — ขอบเขตและลำดับส่งมอบยึดตาราง 3.1 และหัวข้อ 7 ของ PLAN.md
> **ที่มาของข้อเท็จจริงด้านผลิตภัณฑ์:** ผู้ตรวจทางเทคนิคยืนยันจากข้อความสรุปในผลการค้นหา (เปิดหน้าเอกสารทางการโดยตรงไม่ได้) รายการที่ระบุว่า "ต้องยืนยัน" ให้เช็กกับเอกสารทางการก่อนลงมือ

---

## 1. กติกาทางวิศวกรรม (ต้องถือตั้งแต่ commit แรก)

1. **ชั้นบริการเดียวคือสัญญา** — ทุกการกระทำทางธุรกิจเป็นฟังก์ชันใน service layer; `/api/v1` (Hono) เป็นแค่ทางขนส่งบาง ๆ ครอบมัน หน้าร้านที่ render ฝั่งเซิร์ฟเวอร์เรียก service ในโปรเซสเดียวกันสำหรับการอ่าน **ไม่ใช้ Server Actions** และไม่ query ฐานข้อมูลจากเบราว์เซอร์
2. **หลังบ้านและหน้าจอตรวจสภาพเป็นหน้า client-rendered ที่ใช้เฉพาะ `api-client`** อยู่ใน route group ที่ export เป็น static ได้ (หรือแยกเป็น `apps/staff`) — เพื่อให้ห่อด้วย Capacitor เป็นแอปพนักงานได้โดยไม่ต้องเขียนใหม่
3. **การยืนยันสิทธิ์รับได้ทั้ง session cookie และ `Authorization: Bearer`** ตั้งแต่วันแรก พร้อมตรวจ Origin สำหรับคำสั่งที่มาด้วย cookie
4. **วันที่ของธุรกิจเป็นวันตามเวลาไทย** — ช่วงเช่าและช่วงกันชุดเป็น `date` ของ Asia/Bangkok ส่งผ่าน API เป็นสตริง `YYYY-MM-DD` ห้ามแปลงผ่าน JS `Date`; จุดเวลา (instant) เป็น `timestamptz`; มี helper เดียวสำหรับ "วันนี้" = `now() AT TIME ZONE 'Asia/Bangkok'`
5. **เงินเป็นจำนวนเต็มหน่วยสตางค์**
6. **ทุกการเปลี่ยนสถานะเขียน `domain_event` ใน transaction เดียวกัน** และทุกการจอง snapshot ราคา + เวอร์ชันของนโยบายและสัญญา
7. **ไม่ลบแถว ใช้การเปลี่ยนสถานะ** (การจอง ช่วงกันชุด) เพื่อให้รายงานย้อนหลังถูกต้อง
8. **ผู้ให้บริการภายนอกทุกรายอยู่หลัง interface เล็ก ๆ:** `PaymentProvider`, `KycProvider`, `SmsProvider`, `Notifier`, `AuthProvider`, `FileStore` — ห้ามให้ส่วนขยายเฉพาะของ Supabase (pg_jsonschema, pg_net, Vault) อยู่ในตรรกะหลัก

| โฮสต์ | Vercel (ภูมิภาคสิงคโปร์) | request body จำกัด ~4.5 MB → ไฟล์ห้ามผ่าน API |
| ติดตามข้อผิดพลาด | error tracking บนเว็บ, API และ sweep + uptime check | |
| วิเคราะห์ (รุ่น 2) | Postgres view; Metabase และ PostHog เมื่อจำเป็น | |

**ที่ตั้งข้อมูล:** ต้องได้คำตอบจากทนายใน M0 ก่อนเขียนโค้ดที่ผูกกับ Supabase — การย้ายไป Postgres ในไทยภายหลังย้ายได้แค่ตาราง ส่วน Auth และ Storage ต้องทำใหม่ จึงต้องครอบทั้งสองไว้หลัง interface ตั้งแต่ต้น

**ต้นทุนคงที่ช่วงเริ่ม (ต้องยืนยันราคา):** Supabase Pro ~US$25/เดือน · Vercel ~US$20/เดือน · LINE OA ฟรี 300 ข้อความ/เดือน แล้ว ~1,280 บาทเมื่อเกินราว 50 การเช่า/เดือน · SMS OTP และ e-KYC จ่ายตามใช้ · gateway ~1.65% (พร้อมเพย์) + VAT

## 3. โครงสร้างโค้ด: modular monolith

repo เดียว deploy เดียว ฐานข้อมูลเดียว

```
packages/domain          ชนิดข้อมูล schema ตาราง transition ฟังก์ชันคำนวณ (pure)
apps/web/src/core/*      identity, kyc, contracts, payments+ledger, media+inspection,
                         cases, shipments, notifications, config, events, deadlines
apps/web/src/modules/rental   catalog, units, availability, bookings, custody, claims
apps/web/src/app/(store)      หน้าร้าน
apps/web/src/app/(staff)      หลังบ้าน + ตรวจสภาพ (client-rendered)
apps/web/src/app/api/v1       Hono
```

- ขอบเขตบังคับด้วย ESLint `no-restricted-imports`: โมดูล import `core` ได้ แต่ `core` ห้าม import โมดูล และโมดูลห้าม import กันเอง
- Postgres 2 schema: `app` และ `reporting` — ทั้งสองไม่เปิดผ่าน Data API ของ Supabase
- เมนูและสิทธิ์เป็นค่าคงที่ TypeScript
- `domain_event` ทำหน้าที่ outbox สำหรับการส่งออกไประบบภายนอก (sweep เป็นผู้ระบาย)

**ทำตั้งแต่แรกเพราะแก้ทีหลังยาก**
- 4 คอลัมน์บทบาทบน `unit`
- `payment` อ้างสิ่งที่ถูกจ่ายเป็น `(module, ref_type, ref_id)` ไม่ใช่ foreign key ไป `booking`
- สิทธิ์ตามการเป็นสมาชิก `organization` ตรวจใน service layer ผ่าน query helper เดียวที่มีการทดสอบ

**รอจนมีโมดูลที่สองถูกจัดลงแผน:** module registry / manifest, schema แยกต่อโมดูล, outbox แยก — เป็นงานเพิ่ม ไม่ต้องย้ายข้อมูล

## 4. การตั้งค่าแบบไดนามิก (ขอบเขตเฟส 1)

| เรื่อง | รูปแบบ |
|---|---|
| คุณสมบัติชุด | คอลัมน์จริงสำหรับสิ่งที่กรอง/รายงาน (ไซซ์ สี มูลค่า ต้นทุน) + `attributes jsonb` ตรวจด้วย Zod ในแอป |
| ราคา | ขั้นราคาต่อ product (จำนวนวัน → ราคา) |
| นโยบาย | **เอกสาร JSON หนึ่งฉบับต่อหมวด มีเวอร์ชัน** ตรวจด้วย Zod: ตารางมัดจำ เพดานความเสี่ยง ค่าปรับ ค่าเสื่อม ตัวจับเวลา ช่วงกันชน กติกายกเลิก ตารางค่าเสียหาย ช่วงเวลา/ความถี่ของการทวงถาม — แก้จากหน้าตั้งค่ากฎหน้าเดียว (แบบฟอร์ม → ตรวจ → บันทึกเป็นฉบับใหม่ → audit event) **ไม่มีการแก้แถวในฐานข้อมูลโดยตรง** |
| รายการตรวจสภาพ, สัญญา | แม่แบบมีเวอร์ชัน (เป็นหลักฐาน) — เฟส 1 เพิ่มเวอร์ชันผ่าน migration/seed |
| ข้อความแจ้งเตือน | แม่แบบมีเวอร์ชัน |
| ค่าคอมมิชชัน | `fee_schedule` (เฟส 2–3) |

ฟังก์ชันคำนวณราคา มัดจำ และความเสี่ยงเป็น pure function ใน `packages/domain` รับ (ชุด, ผู้เช่า, วัน, วิธีส่ง, นโยบาย) → ผลลัพธ์ที่ snapshot ลงการจอง

**อยู่ในโค้ดโดยเจตนา:** ตาราง transition ของสถานะ · รายการสิทธิ์ · กฎการลงบัญชี

**จะไม่ทำ:** ตัวสร้างฟอร์ม/หน้า/เวิร์กโฟลว์ · ภาษาเขียนกฎ · rule row ตามขอบเขตหลายชั้นพร้อมลำดับความสำคัญ · state machine ที่ผู้ใช้กำหนด · ตาราง attribute–value (EAV) · schema แยกต่อ tenant · หลายสกุลเงิน · microservices / micro-frontend · event sourcing เต็มรูป · โมเดล "service order" ทั่วไปสำหรับธุรกิจที่ยังไม่มี · idempotency layer ทั่วไปทุก endpoint

## 5. โมเดลข้อมูล

**tenant และ organization:** `tenant_id` = ผู้ดำเนินการแพลตฟอร์ม มีค่าเดียวตลอดเฟส 1–3 (สำรองไว้สำหรับ white-label) **การแยกสิทธิ์ทำด้วยบทบาทต่อ `organization` บนแต่ละแถว ไม่ใช่ด้วย tenant** — ในเฟส 2 ผู้ปล่อยเช่า A ต้องไม่เห็นลูกค้าของผู้ปล่อยเช่า B

**4 บทบาทบน `unit`:** `owner_org_id`, `operator_org_id`, `custody_location_id`, `merchant_of_record_org_id` (ค่าเริ่มต้นอยู่บน unit และถูก snapshot ลง `booking` ตอนจอง)

| เอนทิตี | ฟิลด์สำคัญ |
|---|---|
| `organization` | ประเภท (PLATFORM / SHOP / LENDER) สถานะ — เจ้าของชุดทุกรายเป็นองค์กร; ผู้ใช้ถือบทบาทต่อองค์กร |
| `party` | เบอร์โทร (ยืนยันแล้ว), `line_user_id`, วันเกิด |
| `identity_verification` | วิธี (EKYC / COUNTER), ผล, ชื่อ เลขบัตร (ตรวจ checksum) ที่อยู่ — เข้ารหัส, `id_hmac`, `key_version`, ความยินยอม, วันหมดอายุของรูป |
| `trust_profile`, `watchlist_entry` | ระดับและตัวนับ; จับคู่ด้วย HMAC ของเลขบัตร เบอร์โทร และบัญชีธนาคารเท่านั้น (ไม่ใช้ที่อยู่ข้อความอิสระหรือ "อุปกรณ์") |
| `category`, `product` | แม่แบบรายการตรวจ, นโยบาย; ชื่อ ไซซ์ สี รูป ขั้นราคา |
| `unit` | ซีเรียล รหัส QR 4 บทบาท โหมด (OWN / LENDER_MANAGED / PLATFORM_MANAGED) มูลค่าที่ตกลง ต้นทุน เกรด จำนวนครั้งเช่า น้ำหนัก ขนาด ชิ้นส่วน สถานะทางกายภาพ `custody_holder` |
| `unit_fingerprint` (เข้ารหัส) | ตำแหน่งเครื่องหมายลับ รูปใกล้ |
| `policy_version`, `checklist_template`, `contract_version`, `message_template` | ดูหัวข้อ 4 |
| `booking` | ผู้เช่า **unit (ผูกตอนจอง 1 ตัวต่อการจองในเฟส 1)** merchant of record สถานะ วันเริ่ม–วันคืน (date) `due_at` วิธีรับ–คืน snapshot ราคา/นโยบาย การยอมรับสัญญา ช่องทางที่มา ผู้สร้าง (ลูกค้า/พนักงาน) timestamp: packed, shipped, delivered, return_scanned |
| `availability_block` | ดูหัวข้อ 6 |
| `custody_transfer` | unit ชนิด (INTAKE / CHECK_OUT / CHECK_IN / TO_VENDOR / FROM_VENDOR / TRY_ON / RETURN_TO_OWNER) จากใคร ถึงใคร วิธี (COUNTER / MESSENGER / COURIER / MEETUP) การตรวจ การขนส่ง การรับทราบของทั้งสองฝ่าย |
| `inspection`, `condition_finding`, `media_asset` | เวอร์ชันแม่แบบ ผู้ตรวจ (คู่กรณีฝ่ายใดก็ได้) เกรด ผู้รับทราบ; ประเภท ตำแหน่ง ความรุนแรง ที่มา ค่าใช้จ่าย; ที่อยู่ไฟล์ ขนาด SHA-256 (คำนวณฝั่งเซิร์ฟเวอร์) เวลา ผู้อัปโหลด |
| `service_job` | ชนิด (CLEAN / REPAIR) ผู้รับจ้าง ต้นทุน เวลาส่ง–รับ ผล |
| `claim` | ผู้เรียกร้อง ผู้ถูกเรียกร้อง จำนวนเงิน กำหนดเวลา สถานะ คำตัดสิน — การจองปิดไม่ได้ขณะมีเคลมเปิด |
| `shipment` | ขา ผู้ขนส่ง เลขพัสดุ มูลค่าที่แจ้ง น้ำหนักขาออก/ที่ขนส่งรับ เลขซีล เวลาสแกน (พนักงานกรอก + ภาพหน้าจอ) ต้นทุน |
| `payment`, `deposit`, `refund` | ผู้ให้บริการ event id จำนวน สถานะ ชื่อผู้โอน (ถ้ามี) สิ่งที่ถูกจ่าย; สถานะมัดจำ; บัญชีรับคืน หลักฐาน กำหนดเวลา |
| `journal`, `ledger_entry` | บัญชีคู่; ทุก journal รวมเป็นศูนย์ (deferred constraint trigger) |
| `notification` | แม่แบบและเวอร์ชัน ข้อความ ผู้รับ เวลา ผลตอบกลับของ LINE |
| `line_inbound_event` | ข้อความขาเข้าจาก webhook (append-only) |
| `deadline`, `task` | งานตามเวลาและงานบนกระดาน "วันนี้" |
| `domain_event`, `audit_log` | append-only |

**ผังบัญชีเฟส 1:** ธนาคาร · พักรับจาก gateway · หนี้สินมัดจำ · เงินคืนค้างจ่าย · รายได้ค่าเช่า · รายได้ค่าปรับ/ค่าเสียหาย · ค่าใช้จ่าย: ค่าธรรมเนียม gateway, ค่าซัก, ค่าซ่อม, ค่าส่ง, ค่าบรรจุ — เฟส 2–3 เพิ่ม: เจ้าหนี้เจ้าของชุด, คอมมิชชัน, ภาษีหัก ณ ที่จ่าย (บัญชีเป็นข้อมูล)

- ลงค่าธรรมเนียมและยอดสุทธิจากรายการของ gateway **ไม่คำนวณ 1.65% + VAT เอง**
- การกระทบยอดรุ่นแรก = รายงานยอดคงเหลือต่อบัญชี เทียบกับยอดของ gateway และยอดธนาคารที่เจ้าของกรอกรายสัปดาห์
- ยอดมัดจำคงค้างเมื่อนำเข้าจากสเปรดชีตลงเป็น opening entry

## 6. ความพร้อมให้เช่าและการกันจองซ้อน

- `availability_block`: **หนึ่งแถวต่อการจอง** มี `unit_id`, `daterange` แบบ half-open ของวันตามเวลาไทย ครอบ เตรียม + ขนส่งไป + วันเช่า + ขนส่งกลับ + ตรวจ + ซัก + กันชน, `kind` (BOOKING / MAINTENANCE / HOLD), `status`, `expires_at`
- **Exclusion constraint** บน `(unit_id WITH =, period WITH &&) WHERE status = 'active'` (ต้องเปิด `btree_gist`) — ฐานข้อมูลเป็นผู้กันจองซ้อน
- **ผูกชุดตอนจอง:** transaction ที่สร้างการจองเลือก unit จริงและ insert block; constraint violation = "ชุดนี้ไม่ว่าง ลองตัวถัดไป/เต็ม" — พนักงานมีคำสั่ง "สลับชุด" ที่ย้าย block ไป unit อื่นของ product เดียวกันและ band เดียวกันแบบ atomic (ต่าง band ต้องเสนอราคาและขอความยินยอมใหม่)
- **การกันชุดรอจ่ายเงิน:** block มี `expires_at`; transaction การจองลบ block ที่หมดอายุของ unit นั้นก่อน insert (lazy expiry) — ไม่ต้องพึ่งตัวกวาด
- **Block คือแผนการจอง ไม่ใช่การครอบครองจริง:** คืนช้าไม่ขยาย block ไปทับการจองถัดไป; ระบบตรวจด้วย query (unit ยังไม่ check-in และ block ถัดไปเริ่มภายใน N วัน) แล้วสร้างงานช่วยเหลือตาม PLAN.md 3.5
- ช่วงกันชนขึ้นกับวิธีส่ง → query ความพร้อมรับวิธีส่ง/โซนเป็น input และตรวจซ้ำตอน checkout
- ยกเลิกด้วยการเปลี่ยน `status` ไม่ลบแถว

## 7. สถานะ

**สถานะของชุด — เฉพาะสถานะทางกายภาพ** (ความพร้อมให้เช่าไม่เก็บบนชุด)

`IN_STOCK · OUT · RECEIVED · INSPECTING · CLEANING · REPAIR · LOST · RETIRED · RETURNED_TO_OWNER`

**สถานะของการจอง — เฉพาะสถานะที่เกิดจากเหตุการณ์** ("ครบกำหนด" และ "เกินกำหนด" คำนวณจาก `due_at`; ปัญหาและเคลมอยู่ใน `claim`)

| จาก | เหตุการณ์ | ไป | เงื่อนไข |
|---|---|---|---|
| — | สร้างการจอง (ลูกค้าหรือพนักงาน) | PENDING_PAYMENT | ได้ block; ผ่านเพดานความเสี่ยง; การจองแบบส่งของต้องเป็น T1 แล้ว |
| PENDING_PAYMENT | ยืนยันการรับเงิน | CONFIRMED | มัดจำ HELD; ยอมรับสัญญาแล้ว |
| PENDING_PAYMENT | block หมดอายุ | EXPIRED | |
| EXPIRED | เงินเข้าหลังหมดอายุ | CONFIRMED ถ้าได้ block คืน มิฉะนั้นเข้าคิวคืนเงิน + แจ้งเตือน | |
| CONFIRMED | ส่งมอบ (รับทราบที่เคาน์เตอร์/หน้าประตู หรือขนส่งส่งสำเร็จ) | HANDED_OVER | ตรวจขาออกครบ; ตัวตนผ่าน |
| CONFIRMED | ยกเลิก / ไม่มารับ / ตรวจตัวตนไม่ผ่าน | CANCELLED | คืนเงินตามกติกายกเลิก |
| HANDED_OVER | พนักงานสแกนรับคืน | RETURNED | ใช้ได้แม้เกินกำหนด (ค่าปรับคำนวณจากเวลาหยุดนับ) |
| HANDED_OVER | D+7 ไม่มีการคืน | NON_RETURN | |
| NON_RETURN | ชุดกลับมา | RETURNED | ใบแจ้งหนี้เปลี่ยนเป็นค่าปรับภายในเพดาน |
| RETURNED | มัดจำถึงสถานะสุดท้าย + ไม่มีเคลมเปิด + journal สมดุล | CLOSED | ด่านรับคืนต้องผ่าน |
| NON_RETURN | ปิดคดี/ตัดจำหน่ายโดยเจ้าของ | CLOSED | |

- ตาราง transition เป็นข้อมูลใน `packages/domain` และทดสอบทุกคู่ (สถานะ, เหตุการณ์)
- **สถานะมัดจำ:** `REQUIRED → HELD → RELEASING → REFUNDED | PARTLY_APPLIED | FORFEITED` (+ `HELD_PENDING_CLEANING` สำหรับผล "ผ่านแบบกันเงินไว้ก่อน")
- เฟส 1: หนึ่งชุดต่อการจอง — เมื่อรองรับหลายชุด สถานะการส่งมอบย้ายไปอยู่ระดับรายการ

## 8. หลักฐานและการอัปโหลด

- **ไฟล์ไม่ผ่าน API:** API ออก "ตั๋วอัปโหลด" → เบราว์เซอร์อัปโหลดตรงไป Storage แบบ resumable (TUS, chunk 6 MB) → เรียก finalize → งานฝั่งเซิร์ฟเวอร์ stream ไฟล์ที่เก็บแล้วเพื่อบันทึก SHA-256 ขนาด และเวอร์ชันลง `media_asset` + `domain_event` (hash ฝั่งเซิร์ฟเวอร์คือหลักฐาน; hash ที่ client รายงานพิสูจน์อะไรไม่ได้)
- **การจับภาพ — ต้องตัดสินจากการทดสอบสัปดาห์ที่ 1–2:**
  - ทางเลือก ก: `getUserMedia` + `MediaRecorder` ที่ 720p ~2.5 Mbps (ราว 10 MB ต่อ 30 วินาที) — คุมขนาดได้และเป็นการถ่ายสด แต่มีรายงานปัญหาบน iOS เมื่อเปิดเป็นแอปบนหน้าจอ
  - ทางเลือก ข: `<input type="file" capture>` ใช้แอปกล้องของเครื่อง — เสถียรกว่า แต่คลิป 30 วินาทีอาจใหญ่ 30–200 MB ตามการตั้งค่ากล้อง ต้องมีเพดานขนาดฝั่ง client
  - เกณฑ์ผ่าน: คลิป 30 วินาที (≤15 MB) และคลิป 3 นาที อัปโหลดสำเร็จและต่อได้หลังเน็ตหลุด บน iOS Safari, Android Chrome, LINE iOS, LINE Android
- **ผู้เช่าที่เปิดจาก LINE แล้วกล้องใช้ไม่ได้:** ออกลิงก์เฉพาะกิจใช้ครั้งเดียว ผูกกับการจอง อายุราว 30 นาที ให้สิทธิ์แค่อัปโหลดหลักฐานในเบราว์เซอร์ของเครื่อง (ไม่ต้องขอ OTP ใหม่กลางช่วงแจ้งปัญหา 24 ชม.)
- **Bucket:** หลักฐาน (private) แยกจากรูปแคตตาล็อก (public) — เส้นทาง request ออกได้แค่ signed URL สำหรับอัปโหลด/ดาวน์โหลด **การลบทำได้เฉพาะงาน retention ที่ใช้ credential แยก**
- **Retention:** ลบสองขั้น (ทำเครื่องหมาย → ลบจริงอีก 30 วัน) และไม่แตะการจองที่มีเคลมเปิด สถานะ NON_RETURN หรือยังอยู่ในช่วง 3 เดือน/6 เดือนตามกฎหมาย
- **รูปแคตตาล็อก:** สร้าง 3 ขนาดตอนอัปโหลด; ค้นหาด้วย `ILIKE`/`pg_trgm`; ตัวกรองวันที่ใช้ `NOT EXISTS` บน block ที่ active

## 9. การชำระเงิน งานตามเวลา และการแจ้งเตือน

**Webhook ของ gateway**
1. ตรวจลายเซ็นบน raw body
2. insert `(provider, event_id)` ใต้ unique constraint — ซ้ำ = ข้าม
3. **ดึงรายการชำระจากผู้ให้บริการด้วย ID อีกครั้ง** แล้วทำตามสถานะนั้น ไม่เชื่อ payload
4. ตอบ 200 หลัง commit เท่านั้น

- ตั้ง `expires_at` ของ QR = เวลาหมดอายุของ block − 1 นาที (Opn ตั้งรายรายการได้ — ของ Stripe ต้องยืนยันก่อนเลือก gateway)
- หน้าจ่ายเงิน: ปุ่มบันทึกรูป QR ยอดและเลขอ้างอิงเป็นข้อความ นับถอยหลัง polling สถานะ และลิงก์กลับมาทำต่อ — ถาม gateway ว่ามีการสลับไปแอปธนาคารสำหรับผู้ค้าบุคคลธรรมดาหรือไม่
- `PaymentProvider` เฟส 1 = สร้างรายการ + webhook เท่านั้น ไม่ขยายล่วงหน้าเพื่อเฟส 2
- การจองที่พนักงานสร้างใช้วิธีจ่าย `EXTERNAL_TRANSFER` (พนักงานยืนยันจากแอปธนาคารและแนบหลักฐาน) หรือส่งลิงก์จ่ายเงิน

**งานตามเวลา — เฟส 1 ไม่มีตัวกวาดรายนาที**
- กระดาน "วันนี้" ได้รายการครบกำหนด/เกินกำหนด/D+N จาก query บน `due_at` เทียบกับเวลาปัจจุบัน
- Vercel Cron วันละครั้งเรียก `/api/internal/sweep` (ป้องกันด้วย `CRON_SECRET`): สร้างงานตามวัน เตือนกำหนดเวลา ระบาย `domain_event` ที่ต้องส่งออก
- handler เป็น idempotent และจองแถวด้วย `FOR UPDATE SKIP LOCKED`
- **Heartbeat:** sweep เขียน `last_run_at`; ถ้าเก่ากว่า 26 ชม. ขึ้นแถบเตือนบนกระดานและ uptime check ภายนอกแจ้ง — กำหนดร้องทุกข์ 3 เดือนแขวนอยู่กับส่วนนี้
- เปลี่ยนเป็นรายนาทีเมื่อสร้างการแจ้งเตือนอัตโนมัติ

**LINE**
- ข้อความตามขั้นตอนส่งจากปุ่มในหลังบ้านผ่าน Messaging API push และเก็บลง `notification` ตั้งแต่รุ่นแรก — ข้อความที่พิมพ์ใน LINE OA Manager ไม่เข้าระบบ และ API ไม่มีทางอ่านประวัติแชตย้อนหลัง
- เปิด webhook ตั้งแต่ M0 เก็บข้อความขาเข้าทั้งหมด
- แชตอิสระ: ขั้นตอน NON_RETURN มีงาน "ส่งออกแชตจาก OA Manager แล้วแนบ"

## 10. ตัวตนและการเข้าสู่ระบบ

- **ลูกค้า: OTP ทางเบอร์โทรเท่านั้น** ในเฟส 1
  - ผู้ให้บริการ SMS ของไทยผ่าน Send SMS hook (Supabase รองรับในตัวเฉพาะ Twilio, MessageBird, Vonage, Textlocal); รับเฉพาะเบอร์ +66
  - CAPTCHA ที่คำขอ OTP · จำกัดต่อเบอร์และต่อ IP · ตั้งเพดาน SMS ของโปรเจกต์อย่างตั้งใจ (ค่าเริ่มต้นต่ำ) · session อายุยาวเพื่อไม่ให้ลูกค้าเดิมต้องขอ OTP บ่อย
- **LINE เป็นช่องทางที่ผูกกับบัญชี ไม่ใช่วิธีเข้าสู่ระบบ:** หลังเข้าสู่ระบบด้วย OTP ภายใน LIFF ส่ง `liff.getIDToken()` ไป `/api/v1/me/line-link` → ตรวจกับ endpoint verify ของ LINE และ channel ID → เก็บ `line_user_id` (LINE Login channel และ Messaging API channel อยู่ใต้ provider เดียวกันเพื่อให้ userId ตรงกัน) — LINE Login ผ่าน custom OIDC ของ Supabase ไม่น่าใช้ได้ตรง ๆ (web login เซ็นด้วย HS256) ถ้าต้องการภายหลังให้ทำเป็น OAuth2 ธรรมดาและพิสูจน์ด้วย spike หนึ่งวันก่อน
- **พนักงาน:** อีเมล + รหัสผ่าน + TOTP; เส้นทางหลังบ้านต้องมี claim `aal2`; บัญชีเจ้าของคนแรกสร้างด้วย seed script; ไม่มีการสมัครเข้าองค์กรเอง

## 11. ความปลอดภัยของข้อมูล

- **บทบาทฐานข้อมูลสองตัวตั้งแต่ migration แรก:** `owner` (ใช้เฉพาะ migration) และ `app_runtime` (ที่ Vercel ใช้: ไม่ใช่เจ้าของตาราง ไม่มี BYPASSRLS; บน `domain_event` และ `audit_log` มีแค่ INSERT + SELECT ไม่มี TRUNCATE) + trigger `BEFORE UPDATE OR DELETE` ที่ raise บนสองตารางนี้ — ถ้าเชื่อมด้วยบทบาทเจ้าของตารางตามค่าเริ่มต้น การเพิกถอนสิทธิ์และ RLS จะไม่มีผลใด ๆ
- เฟส 1 ไม่พึ่ง RLS: ตารางทั้งหมดอยู่ใน schema ที่ Data API ไม่เปิด และตรวจ Security Advisor ของ Supabase
- **กุญแจ:** กุญแจเข้ารหัสและกุญแจ HMAC เก็บเป็น sensitive environment variable ของ Vercel หรือ cloud KMS — ไม่เก็บในฐานข้อมูล (Vault อ่านได้ด้วย credential ของฐานข้อมูล); มี `key_version` สำหรับหมุนกุญแจ
- บันทึกทุกครั้งที่พนักงานเปิดดูข้อมูลตัวตน; ลิงก์ไฟล์อายุสั้น
- Metabase (ถ้าใช้) ใช้บทบาทอ่านอย่างเดียวที่เห็นเฉพาะ schema `reporting` ไม่เห็นตารางตัวตน
- **PDPA:** ประกาศความเป็นส่วนตัว · ความยินยอมแยกสำหรับการตลาด · ความยินยอมโดยชัดแจ้งสำหรับการเทียบใบหน้า · ขั้นตอนคำขอของเจ้าของข้อมูล (30 วัน) · ขั้นตอนแจ้งเหตุละเมิด (72 ชม.) · การเก็บข้อมูลนอกประเทศ: ให้ทนายยืนยันว่าเข้าข้อยกเว้นของการเก็บบน cloud หรือไม่ ถ้าไม่ ต้องมีข้อตกลงประมวลผลข้อมูลพร้อมข้อสัญญาโอนข้อมูล

## 12. สำรองข้อมูล สภาพแวดล้อม และการทดสอบ (อยู่ในสัปดาห์ 1–2)

**สำรองข้อมูล** — Supabase Pro สำรองฐานข้อมูลรายวันย้อนหลัง 7 วัน และ **ไฟล์ใน Storage ไม่อยู่ในชุดสำรองใด ๆ**
- `pg_dump` ทุกคืนไปยัง bucket นอก Supabase (เก็บ 30–90 วัน)
- sync bucket หลักฐานทุกคืนไปผู้ให้บริการที่สอง แบบมี versioning หรือ object lock
- ซ้อมกู้ข้อมูลหนึ่งครั้งก่อนเปิดตัว

**สภาพแวดล้อม:** โปรเจกต์ Supabase ที่สอง + โดเมน staging คงที่ + LINE channel / LIFF / OA และ key ทดสอบของ gateway ของตัวเอง (webhook และ LIFF ต้องใช้ URL คงที่ preview URL ของ Vercel ไม่พอ)

**CI:** typecheck · รัน migration บน Postgres ชั่วคราวที่มี `btree_gist` · test

**การทดสอบที่ต้องมี**
- table-driven test ครบทุก transition ของสถานะ
- property test: ทุกการลงบัญชีทำให้ ledger สมดุล และหนี้สินมัดจำต่อการจองกลับเป็นศูนย์เมื่อ CLOSED
- concurrency test: ยิงการจองพร้อมกันใส่ unit เดียวบน Postgres จริง
- เล่น webhook payload ที่บันทึกไว้ซ้ำสองรอบและสลับลำดับ
- browser happy path หนึ่งเส้นในโหมดทดสอบของ gateway
- test ของวันที่ข้ามเที่ยงคืนเวลาไทย

## 13. รายงาน

- schema `reporting` เป็น view ธรรมดา; `unit_day` = `generate_series` × units join กับ block (ที่ยกเลิกด้วยสถานะ) และเหตุการณ์สถานะ ใช้วันตามเวลาไทย — materialize เมื่อรายงานช้ากว่าราว 1 วินาทีเท่านั้น
- ทุกแถวมี owner / operator / โหมด → รายงานผู้ปล่อยเช่าคือ query เดิมที่กรองตามเจ้าของ
- อัตราอัปโหลดล้มเหลวเก็บจากเหตุการณ์ของตั๋วอัปโหลดที่ไม่ถูก finalize

- **โครงสร้างเงิน A คือ integration ใหม่:** onboarding ผู้ปล่อยเช่ากับผู้ให้บริการ กติกาแบ่งจ่าย การหน่วงเงิน webhook การจ่ายออก การคืนเงินของรายการที่แบ่งจ่าย และกฎการลงบัญชีชุดที่สอง — ประเมินเมื่อผู้ให้บริการยืนยันเงื่อนไข
- เฟส 3: `custody_transfer` ชนิด INTAKE / RETURN_TO_OWNER, รหัสตำแหน่งในคลัง, ใบแจ้งยอดผู้ปล่อยเช่าจาก ledger
