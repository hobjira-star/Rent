# ข้อกำหนดทางเทคนิค (Rent)

> เอกสารสำหรับนักพัฒนา คู่กับ [PLAN.md](./PLAN.md) — ขอบเขตและลำดับส่งมอบยึดตารางหัวข้อ 3.1 และหัวข้อ 7.1 ของ PLAN.md (รุ่น 1 แบ่งเป็นช่วง ก–ง)
> **ความน่าเชื่อถือของข้อเท็จจริงด้านผลิตภัณฑ์:** ผู้ตรวจทางเทคนิคเปิดหน้าเอกสารทางการโดยตรงไม่ได้ ข้อเท็จจริงบางส่วนยืนยันจากข้อความสรุปในผลการค้นหา และบางส่วนมาจากความรู้ของผู้ตรวจที่ยังไม่ได้ยืนยัน — รายการที่ต้องเช็กกับเอกสารทางการก่อนลงมืออยู่ในหัวข้อ 16

---

## 1. กติกาทางวิศวกรรม (ต้องถือตั้งแต่ commit แรก)

1. **ชั้นบริการเดียวคือสัญญา** — ทุกการกระทำทางธุรกิจเป็นฟังก์ชันใน service layer; `/api/v1` (Hono) เป็นแค่ทางขนส่งบาง ๆ ครอบมัน หน้าร้านที่ render ฝั่งเซิร์ฟเวอร์เรียก service ในโปรเซสเดียวกันสำหรับการอ่าน **ไม่ใช้ Server Actions** และไม่ query ฐานข้อมูลจากเบราว์เซอร์
2. **หลังบ้านและหน้าจอตรวจสภาพเป็นแอปแยก `apps/staff`** แบบ client-only ที่ build เป็นไฟล์ static และใช้เฉพาะ `api-client` — เพื่อให้ห่อด้วย Capacitor เป็นแอปพนักงานได้โดยไม่ต้องเขียนใหม่ (static export ของ Next.js ใช้กับทั้งแอป จึงแยกออกจาก `apps/web` ที่มีหน้าร้าน render ฝั่งเซิร์ฟเวอร์และ route handler) CI ต้อง build `apps/staff` แบบ static ทุกครั้ง
3. **การยืนยันสิทธิ์รับได้ทั้ง session cookie และ `Authorization: Bearer`** ตั้งแต่วันแรก พร้อมตรวจ Origin สำหรับคำสั่งที่มาด้วย cookie
4. **วันที่ของธุรกิจเป็นวันตามเวลาไทย** — ช่วงเช่าและช่วงกันชุดเป็น `date` ของ Asia/Bangkok ส่งผ่าน API เป็นสตริง `YYYY-MM-DD` ห้ามแปลงผ่าน JS `Date`; จุดเวลา (instant) เป็น `timestamptz`; มี helper เดียวสำหรับ "วันนี้" = `now() AT TIME ZONE 'Asia/Bangkok'`; วันทำการคำนวณจากปฏิทินวันและเวลาทำการในนโยบาย
5. **เงินเป็นจำนวนเต็มหน่วยสตางค์**
6. **ทุกการเปลี่ยนสถานะเขียน `domain_event` ใน transaction เดียวกัน** และทุกการจอง snapshot ราคา + เวอร์ชันของนโยบายและสัญญา
7. **ไม่ลบแถว ใช้การเปลี่ยนสถานะ** (การจอง ช่วงกันชุด) เพื่อให้รายงานย้อนหลังถูกต้อง
8. **ผู้ให้บริการภายนอกทุกรายอยู่หลัง interface เล็ก ๆ:** `PaymentProvider`, `KycProvider`, `SmsProvider`, `Notifier`, `AuthProvider`, `FileStore` — ห้ามให้ส่วนขยายเฉพาะของ Supabase (pg_jsonschema, pg_net, Vault) อยู่ในตรรกะหลัก

## 2. Stack

| ส่วน | ที่เลือก | หมายเหตุ |
|---|---|---|
| หน้าร้าน + API | Next.js (major ล่าสุดที่ stable) + TypeScript ใน `apps/web` | หน้าร้าน render ฝั่งเซิร์ฟเวอร์เพื่อ SEO; Hono ภายใต้ `/api/v1` |
| หลังบ้าน | `apps/staff` — client-only SPA build เป็น static | ดูกติกาข้อ 2 |
| แพ็กเกจร่วม | pnpm workspace: `packages/domain` (ชนิดข้อมูล, Zod schema, ตาราง transition, ฟังก์ชันราคา/มัดจำ/ความเสี่ยง), `packages/api-client` (Hono typed RPC client) | เพิ่ม OpenAPI เมื่อมี client ที่ไม่ใช่ TypeScript |
| Idempotency | idempotency key เฉพาะ: สร้างการจอง, สร้างรายการชำระ, บันทึกว่าคืนเงินแล้ว | ที่เหลือใช้ unique constraint และ transition แบบ `WHERE status = <ที่คาด>` |
| ฐานข้อมูล | Postgres บน Supabase Pro (สิงคโปร์) + Drizzle + SQL migration | เชื่อมผ่าน Supavisor pooler; transaction mode ต้องปิด prepared statements (`prepare: false`) — จดไว้ใน README |
| Auth | Supabase Auth หลัง `AuthProvider` | หัวข้อ 10 |
| ไฟล์ | Supabase Storage หลัง `FileStore` | หัวข้อ 8 และ 11 |
| งานตามเวลา | Vercel Cron วันละครั้ง → `/api/internal/sweep`; งานสำรองข้อมูลและงานลบตามอายุรันเป็น scheduled workflow ของ GitHub Actions | หัวข้อ 9 และ 12 |
| โฮสต์ | Vercel (ภูมิภาคสิงคโปร์) | request body จำกัด ~4.5 MB → ไฟล์ห้ามผ่าน API |
| ติดตามข้อผิดพลาด | error tracking บนเว็บ, API และ sweep + uptime check | |
| รายงาน | Postgres view ใน schema `reporting` (รุ่น 1); Metabase และ PostHog เมื่อจำเป็น (รุ่น 2) | หัวข้อ 13 |

**ที่ตั้งข้อมูล:** ต้องได้คำตอบจากทนายใน M0 ก่อนเขียนโค้ดที่ผูกกับ Supabase — การย้ายไป Postgres ในไทยภายหลังย้ายได้แค่ตาราง ส่วน Auth และ Storage ต้องทำใหม่ จึงต้องครอบทั้งสองไว้หลัง interface ตั้งแต่ต้น

**ต้นทุนคงที่ช่วงเริ่ม (ต้องยืนยันราคา):** Supabase Pro ~US$25/เดือน · Vercel ~US$20/เดือน · LINE OA ฟรี 300 ข้อความ/เดือน แล้ว ~1,280 บาทเมื่อเกินราว 50 การเช่า/เดือน · SMS OTP และ e-KYC จ่ายตามใช้ · gateway ~1.65% (พร้อมเพย์) + VAT

## 3. โครงสร้างโค้ด: modular monolith

repo เดียว ฐานข้อมูลเดียว API เดียว

```
packages/domain             ชนิดข้อมูล schema ตาราง transition ฟังก์ชันคำนวณ (pure)
packages/api-client         typed client ของ /api/v1
apps/web/src/core/*         identity, kyc, contracts, payments+ledger, media+inspection,
                            claims, shipments, notifications, config, events, deadlines
apps/web/src/modules/rental catalog, units, availability, bookings, custody
apps/web/src/app/(store)    หน้าร้าน (server-rendered)
apps/web/src/app/api/v1     Hono
apps/staff                  หลังบ้าน + ตรวจสภาพ (client-only, static build)
```

- ขอบเขตบังคับด้วย ESLint `no-restricted-imports`: โมดูล import `core` ได้ แต่ `core` ห้าม import โมดูล และโมดูลห้าม import กันเอง
- Postgres 2 schema: `app` และ `reporting` — ทั้งสองไม่เปิดผ่าน Data API ของ Supabase
- เมนูและสิทธิ์เป็นค่าคงที่ TypeScript
- `domain_event` ทำหน้าที่ outbox สำหรับการส่งออกไประบบภายนอก (sweep เป็นผู้ระบาย)
- "เคส" ใน PLAN.md กับ `claim` คือเอนทิตีเดียวกัน อยู่ใน `core/claims`

**ทำตั้งแต่แรกเพราะแก้ทีหลังยาก**
- 4 คอลัมน์บทบาทบน `unit`
- `payment` อ้างสิ่งที่ถูกจ่ายเป็น `(module, ref_type, ref_id)` ไม่ใช่ foreign key ไป `booking`
- สิทธิ์ตามการเป็นสมาชิก `organization` ตรวจใน service layer ผ่าน query helper เดียวที่มีการทดสอบ

**รอจนมีโมดูลที่สองถูกจัดลงแผน:** module registry / manifest, schema แยกต่อโมดูล, outbox แยก — เป็นงานเพิ่ม ไม่ต้องย้ายข้อมูล

## 4. การตั้งค่าแบบไดนามิก (ขอบเขตเฟส 1)

| เรื่อง | รูปแบบ |
|---|---|
| คุณสมบัติชุด | คอลัมน์จริงสำหรับสิ่งที่กรอง/รายงาน (ไซซ์ สี มูลค่า ต้นทุน) + `attributes jsonb` ตรวจด้วย Zod ในแอป |
| ราคา | ขั้นราคาต่อ product (จำนวนวัน → ราคา) |
| นโยบาย | **เอกสาร JSON หนึ่งฉบับต่อหมวด มีเวอร์ชัน** ตรวจด้วย Zod: ตารางมัดจำ · เพดานความเสี่ยง (ต่อผู้เช่าและทั้งร้าน) · วิธีรับ–ส่งที่อนุญาตต่อ band · ค่าปรับ · ค่าเสื่อม · ตัวจับเวลาและระยะกันชุด · ช่วงกันชน · วันและเวลาทำการ · กติกายกเลิก · ตารางค่าเสียหาย · ช่วงเวลา/ความถี่ของการทวงถาม · อายุการเก็บข้อมูล — แก้จากหน้าตั้งค่ากฎหน้าเดียว (แบบฟอร์ม → ตรวจ → บันทึกเป็นฉบับใหม่ → audit event) **ไม่มีการแก้แถวในฐานข้อมูลโดยตรง** |
| รายการตรวจสภาพ, สัญญา | แม่แบบมีเวอร์ชัน (เป็นหลักฐาน) — เฟส 1 เพิ่มเวอร์ชันผ่าน migration/seed; สัญญาชั่วคราวของ M0 โหลดเป็นเวอร์ชัน 0 |
| ข้อความแจ้งเตือน | แม่แบบมีเวอร์ชัน |
| ค่าคอมมิชชัน | `fee_schedule` — เพิ่มในเฟส 2–3 (เป็นตารางใหม่ ไม่ต้องย้ายข้อมูล) |

ฟังก์ชันคำนวณราคา มัดจำ และความเสี่ยงเป็น pure function ใน `packages/domain` รับ (ชุด, ผู้เช่า, วัน, วิธีส่ง, นโยบาย, การจองที่เปิดอยู่ของกลุ่มที่เชื่อมโยง) → ผลลัพธ์ที่ snapshot ลงการจอง

**อยู่ในโค้ดโดยเจตนา:** ตาราง transition ของสถานะ · รายการสิทธิ์ · กฎการลงบัญชี

**จะไม่ทำ:** ตัวสร้างฟอร์ม/หน้า/เวิร์กโฟลว์ · ภาษาเขียนกฎ · rule row ตามขอบเขตหลายชั้นพร้อมลำดับความสำคัญ · state machine ที่ผู้ใช้กำหนด · ตาราง attribute–value (EAV) · schema แยกต่อ tenant · หลายสกุลเงิน · microservices / micro-frontend · event sourcing เต็มรูป · โมเดล "service order" ทั่วไปสำหรับธุรกิจที่ยังไม่มี · idempotency layer ทั่วไปทุก endpoint

## 5. โมเดลข้อมูล

**tenant และ organization:** `tenant_id` = ผู้ดำเนินการแพลตฟอร์ม มีค่าเดียวตลอดเฟส 1–3 (สำรองไว้สำหรับ white-label) **การแยกสิทธิ์ทำด้วยบทบาทต่อ `organization` บนแต่ละแถว ไม่ใช่ด้วย tenant** — ในเฟส 2 ผู้ปล่อยเช่า A ต้องไม่เห็นลูกค้าของผู้ปล่อยเช่า B

**4 บทบาทบน `unit`:** `owner_org_id`, `operator_org_id`, `custody_location_id`, `merchant_of_record_org_id` (ค่าเริ่มต้นอยู่บน unit และถูก snapshot ลง `booking` ตอนจอง)

| เอนทิตี | ฟิลด์สำคัญ |
|---|---|
| `organization` | ประเภท (PLATFORM / SHOP / LENDER) สถานะ — เจ้าของชุดทุกรายเป็นองค์กร; ผู้ใช้ถือบทบาทต่อองค์กร |
| `location` | ที่อยู่/คลัง/ราว-ช่อง ที่ `custody_location_id` ชี้ไป |
| `party` | เบอร์โทร (ยืนยันแล้ว), `line_user_id`, วันเกิด (กรอกเอง → ยืนยันจากบัตร) |
| `identity_verification` | วิธี (EKYC / COUNTER), ผล, ชื่อ เลขบัตร (ตรวจ checksum) ที่อยู่ตามบัตร ที่อยู่ปัจจุบัน — เข้ารหัส, `id_hmac` (**unique: เลขบัตรหนึ่งเลข = หนึ่ง party**), `key_version`, ความยินยอม, รูปบัตรปิดทับและรูปส่งมอบ พร้อมวันครบกำหนดลบ |
| `party_bank_account` | เลขบัญชี (เข้ารหัส), HMAC, ชื่อเจ้าของบัญชี, วิธีตรวจ (โอน 1 บาท / API / ชื่อที่แอปธนาคารแสดง), เวลาและผู้ตรวจ — เงินคืนออกได้เฉพาะบัญชีในตารางนี้ที่ตรวจแล้วและผูกกับตัวตนที่ยืนยันแล้ว |
| `trust_profile`, `watchlist_entry` | ระดับ (T0/T1/T2), band สูงสุดที่คืนเรียบร้อย, ตัวนับ; รายการเฝ้าระวังเป็น HMAC ของเลขบัตร เบอร์โทร บัญชีธนาคาร |
| `category`, `product` | แม่แบบรายการตรวจ, นโยบาย; ชื่อ ไซซ์ สี รูป ขั้นราคา |
| `unit` | ซีเรียล รหัส QR 4 บทบาท โหมด (OWN / LENDER_MANAGED / PLATFORM_MANAGED) มูลค่าที่ตกลง ต้นทุน เกรด จำนวนครั้งเช่า น้ำหนัก ขนาด ชิ้นส่วน สถานะทางกายภาพ `custody_holder` |
| `unit_fingerprint` (เข้ารหัส) | ตำแหน่งเครื่องหมายลับ รูปใกล้ |
| `policy_version`, `checklist_template`, `contract_version`, `message_template` | หัวข้อ 4 |
| `booking` | ผู้เช่า · **unit (ผูกตอนจอง 1 ตัวต่อการจองในเฟส 1)** · merchant of record · สถานะ · วันเริ่ม–วันคืน (date) · `due_at` · วิธีรับ–คืน · snapshot ราคา/นโยบาย · การยอมรับสัญญา (เวอร์ชัน, วิธี: PAPER / OTP_SESSION / ONE_TIME_LINK, หลักฐาน) · ผู้รับแทน · ผู้ปกครองที่เป็นคู่สัญญา · ธงที่ต้องตรวจ (ชื่อผู้โอนไม่ตรง, เกินเพดาน, ที่อยู่ซ้ำ) และผู้ตรวจ · `replaces_booking_id` · ช่องทางที่มา · ผู้สร้าง (ลูกค้า/พนักงาน) · timestamp: packed, shipped, delivered, return_scanned |
| `availability_block` | หัวข้อ 6 |
| `custody_transfer` | unit ชนิด (INTAKE / CHECK_OUT / CHECK_IN / TO_VENDOR / FROM_VENDOR / TRY_ON / RETURN_TO_OWNER) จากใคร ถึงใคร วิธี (COUNTER / MESSENGER / COURIER / MEETUP) การตรวจ การขนส่ง การรับทราบของทั้งสองฝ่าย (วิธีเดียวกับการยอมรับสัญญา) |
| `inspection`, `condition_finding`, `media_asset` | เวอร์ชันแม่แบบ ผู้ตรวจ (คู่กรณีฝ่ายใดก็ได้) เกรด ผลด่านรับคืน ผู้รับทราบ; ประเภท ตำแหน่ง ความรุนแรง ที่มา ค่าใช้จ่าย; ที่อยู่ไฟล์ ขนาด SHA-256 (คำนวณฝั่งเซิร์ฟเวอร์) เวลา ผู้อัปโหลด |
| `service_job` | ชนิด (CLEAN / REPAIR) ผู้รับจ้าง ต้นทุน เวลาส่ง–รับ ผล |
| `claim` | ผู้เรียกร้อง ผู้ถูกเรียกร้อง จำนวนเงิน กำหนดเวลา สถานะ คำตัดสิน — การจองปิดไม่ได้ขณะมีเคลมเปิด |
| `invoice` | ใบแจ้งหนี้ถึงผู้เช่า (ค่าเสียหายเกินมัดจำ, มูลค่าชุดกรณีไม่คืน) ยอด สถานะ กำหนดเตือน 6 เดือน — การจองปิดได้แม้ยังมีใบแจ้งหนี้ค้าง โดยติดตามต่อบนใบแจ้งหนี้ |
| `shipment` | ขา ผู้ขนส่ง เลขพัสดุ ที่อยู่จัดส่ง มูลค่าที่แจ้ง น้ำหนักขาออก/ที่ขนส่งรับ เลขซีล เลขป้ายกันใส่ เวลาสแกน (พนักงานกรอก + ภาพหน้าจอ) ต้นทุน |
| `payment`, `deposit`, `refund` | ผู้ให้บริการ event id จำนวน สถานะ ชื่อผู้โอน สิ่งที่ถูกจ่าย ผู้ยืนยัน (สำหรับ `EXTERNAL_TRANSFER`); สถานะมัดจำ; บัญชีปลายทาง (อ้าง `party_bank_account`) หลักฐาน กำหนดเวลา |
| `journal`, `ledger_entry` | บัญชีคู่; ทุก journal รวมเป็นศูนย์ (deferred constraint trigger) |
| `notification` | แม่แบบและเวอร์ชัน ข้อความ ผู้รับ ช่องทาง (LINE / SMS / บันทึกการติดต่อด้วยมือ) เวลา ผลตอบกลับ |
| `line_inbound_event` | ข้อความขาเข้าจาก webhook (append-only) |
| `stock_count` | รอบนับ ผู้นับ ชุดที่พบ/ไม่พบ |
| `deadline`, `task` | งานตามเวลาและงานในรายการประจำวัน |
| `domain_event`, `audit_log` | append-only |

**กลุ่มที่เชื่อมโยงกัน** (ใช้กับเพดานความเสี่ยงตั้งแต่ช่วง ค): จับคู่อัตโนมัติด้วย `id_hmac`, เบอร์โทร และ HMAC ของบัญชีธนาคาร · ชื่อผู้โอนและที่อยู่จัดส่ง (normalize เป็นรหัสไปรษณีย์ + เลขที่บ้าน) สร้างธงให้คนตรวจเท่านั้น

**ผังบัญชีเฟส 1:** ธนาคาร · พักรับจาก gateway · หนี้สินมัดจำ · เงินคืนค้างจ่าย · ลูกหนี้ผู้เช่า · รายได้ค่าเช่า · รายได้ค่าปรับ/ค่าเสียหาย · ค่าใช้จ่าย: ค่าธรรมเนียม gateway, ค่าซัก, ค่าซ่อม, ค่าส่ง, ค่าบรรจุ, ส่วนลดชดเชย, หนี้สูญ/ตัดจำหน่าย, ชุดสูญหาย — เฟส 2–3 เพิ่ม: เจ้าหนี้เจ้าของชุด, คอมมิชชัน, ภาษีหัก ณ ที่จ่าย (บัญชีเป็นข้อมูล)

- ลงค่าธรรมเนียมและยอดสุทธิจากรายการของ gateway **ไม่คำนวณ 1.65% + VAT เอง**
- การกระทบยอดรุ่นแรก = รายงานยอดคงเหลือต่อบัญชี เทียบกับยอดของ gateway และยอดธนาคารที่เจ้าของกรอกรายสัปดาห์ พร้อมรายการ `EXTERNAL_TRANSFER` ที่พนักงานยืนยันเอง
- ยอดมัดจำคงค้างเมื่อนำเข้าจากสเปรดชีตลงเป็น opening entry

## 6. ความพร้อมให้เช่าและการกันจองซ้อน

- `availability_block`: **หนึ่งแถวต่อการจอง** มี `unit_id`, `daterange` แบบ half-open ของวันตามเวลาไทย ครอบ เตรียม + ขนส่งไป + วันเช่า + ขนส่งกลับ + ตรวจ + ซัก + กันชน, `kind` (HOLD / BOOKING / MAINTENANCE), `status` (active / expired / cancelled), `expires_at`
- **Exclusion constraint** บน `(unit_id WITH =, period WITH &&) WHERE status = 'active'` (ต้องเปิด `btree_gist`) — ฐานข้อมูลเป็นผู้กันจองซ้อน
- **ผูกชุดตอนจอง:** transaction ที่สร้างการจองเลือก unit จริงและ insert block; constraint violation = "ชุดนี้ไม่ว่าง"
- **การกันชุดรอจ่ายเงิน (lazy expiry):** block ชนิด HOLD มี `expires_at` (15 นาทีสำหรับลูกค้าจองเอง นับจากกดจ่าย; 24 ชม. สำหรับการจองที่พนักงานสร้าง) — transaction ที่จะจอง unit เดียวกัน **เปลี่ยนสถานะ** block ที่หมดอายุเป็น `expired` (ไม่ลบ) และย้ายการจองเดิมไป EXPIRED ใน transaction เดียวกัน ก่อน insert ของตัวเอง · ทุก query ความพร้อมถือว่า block ที่ `expires_at <= now()` ไม่มีอยู่ · เมื่อ CONFIRMED เปลี่ยน `kind` เป็น BOOKING และล้าง `expires_at`
- **Block คือแผนการจอง ไม่ใช่การครอบครองจริง:** คืนช้าไม่ขยาย block ไปทับการจองถัดไป; ระบบตรวจด้วย query (unit ยังไม่ check-in และ block ถัดไปเริ่มภายใน N วัน) แล้วสร้างงานช่วยเหลือตาม PLAN.md 3.5
- **เปลี่ยนวัน / เช่าต่อ** = อัปเดตช่วงของ block แบบ atomic; constraint violation = ไม่ว่าง
- **สลับชุด** = ย้าย block ไป unit อื่น (product ใดก็ได้) แบบ atomic — ถ้า band หรือราคาต่าง ต้อง snapshot ราคา/มัดจำใหม่และขอการยอมรับใหม่ เก็บหรือคืนส่วนต่างมัดจำ
- **ชุดทดแทนหลังส่งมอบแล้ว** = ปิดการจองเดิมผ่าน RETURNED ตามผลเคลม แล้วสร้างการจองใหม่ไม่คิดเงินที่อ้าง `replaces_booking_id`
- ช่วงกันชนขึ้นกับวิธีส่ง → query ความพร้อมรับวิธีส่ง/โซนเป็น input และตรวจซ้ำตอน checkout
- ยกเลิกด้วยการเปลี่ยน `status` ไม่ลบแถว

| RETURNED | มัดจำถึงสถานะสุดท้าย + ไม่มีเคลมเปิด + journal สมดุล | CLOSED | ใบแจ้งหนี้ค้างได้ |
| NON_RETURN | ปิดคดี/ตัดจำหน่ายโดยเจ้าของ | CLOSED | |

- ตาราง transition เป็นข้อมูลใน `packages/domain` และทดสอบทุกคู่ (สถานะ, เหตุการณ์)
- **สถานะมัดจำ:** `REQUIRED → HELD → RELEASING → REFUNDED | PARTLY_APPLIED | FORFEITED` (+ `HELD_PENDING_CLEANING`) — **`HELD → RELEASING` และ `HELD → HELD_PENDING_CLEANING` ต้องมีผลด่านรับคืน = ผ่าน บันทึกแล้ว** (ข้อยกเว้นเดียว: ครบช่วงตรวจรับ + 1 วันทำการแล้วยังไม่ได้ทำด่าน ระบบแจ้งเจ้าของและปล่อยตามกติกา PLAN.md 3.4)
- **การตรวจเพดานความเสี่ยง** รันใน transaction ของการจองหลัง `SELECT ... FOR UPDATE` บน `trust_profile` ของผู้เช่า (และหนึ่งแถวสำหรับเพดานทั้งร้าน) นับการจองที่เปิดอยู่ = PENDING_PAYMENT ที่ยังไม่หมดอายุ, CONFIRMED, HANDED_OVER, NON_RETURN และ RETURNED ที่ยังไม่ CLOSED ของทั้งกลุ่มที่เชื่อมโยง — รันซ้ำเมื่อยืนยันการรับเงิน เมื่อรู้ตัวตนครั้งแรก (เคาน์เตอร์หรือ e-KYC) และเมื่อส่งมอบ; ถ้าเกิน: เก็บมัดจำเพิ่มให้ครบ 100% หรือยกเลิกโดยคืนเงิน
- เฟส 1: หนึ่งชุดต่อการจอง — เมื่อรองรับหลายชุด สถานะการส่งมอบย้ายไปอยู่ระดับรายการ

## 8. หลักฐานและการอัปโหลด

- **ไฟล์ไม่ผ่าน API:** API ออก "ตั๋วอัปโหลด" → เบราว์เซอร์อัปโหลดตรงไป Storage แบบ resumable (TUS, chunk 6 MB) → เรียก finalize → **finalize stream ไฟล์ที่เก็บแล้วเพื่อบันทึก SHA-256 ขนาด และเวอร์ชันลง `media_asset` + `domain_event`** (ตั้ง max duration ของ function ให้พอ; sweep รายวัน hash ซ้ำไฟล์ที่ยังไม่มี hash) — hash ฝั่งเซิร์ฟเวอร์คือหลักฐาน; hash ที่ client รายงานพิสูจน์อะไรไม่ได้ · ตั้งเพดานขนาดไฟล์ของ Storage อย่างชัดเจน
- **การจับภาพ — ต้องตัดสินจากการทดสอบช่วง ก:**
  - ทางเลือก ก: `getUserMedia` + `MediaRecorder` ที่ 720p ~2.5 Mbps (ราว 10 MB ต่อ 30 วินาที, ราว 55 MB ต่อ 3 นาที) — คุมขนาดได้และเป็นการถ่ายสด แต่มีรายงานปัญหาบน iOS เมื่อเปิดเป็นแอปบนหน้าจอ
  - ทางเลือก ข: `<input type="file" capture>` ใช้แอปกล้องของเครื่อง — เสถียรกว่า แต่ไฟล์ใหญ่ตามการตั้งค่ากล้อง ต้องมีเพดานขนาดฝั่ง client
  - **เกณฑ์ผ่าน:** คลิป 30 วินาที ≤15 MB และคลิป 3 นาที ≤60 MB ด้วยทางเลือก ก อัปโหลดผ่าน 4G สำเร็จและต่อได้หลังเน็ตหลุด บน 5 แบบ: iOS Safari, iOS แบบติดตั้งบนหน้าจอ, Android Chrome, LINE iOS, LINE Android — แบบใดที่ ก ไม่ผ่านให้ใช้ ข พร้อมเพดานขนาดและเวลาอัปโหลดที่วัดได้จริง และบันทึกผลว่าพนักงานควรใช้โหมดไหน
- **ผู้เช่าที่เปิดจาก LINE แล้วกล้องใช้ไม่ได้:** ออกลิงก์เฉพาะกิจใช้ครั้งเดียว ผูกกับการจอง อายุราว 30 นาที ให้สิทธิ์แค่อัปโหลดหลักฐานในเบราว์เซอร์ของเครื่อง (ไม่ต้องขอ OTP ใหม่กลางช่วงแจ้งปัญหา 24 ชม.) — ลิงก์แบบเดียวกันใช้กับการยอมรับสัญญาและรับทราบสภาพของการจองที่พนักงานสร้าง
- **Bucket:** หลักฐาน (private) แยกจากรูปแคตตาล็อก (public) — สิทธิ์ของ credential ดูหัวข้อ 11
- **Retention:** ตามอายุการเก็บใน PLAN.md 3.3 ชั้นที่ 1 (รูปบัตรและรูปส่งมอบ 30 วันหลัง CLOSED; หลักฐานตรวจสภาพ 12 เดือนหลัง CLOSED; หยุดนับเมื่อมีเคลมเปิด, NON_RETURN หรือใบแจ้งหนี้ค้าง) — ลบสองขั้น: ทำเครื่องหมาย → ลบจริงอีก 30 วัน
- **รูปแคตตาล็อก:** สร้าง 3 ขนาดตอนอัปโหลด; ค้นหาด้วย `ILIKE`/`pg_trgm`; ตัวกรองวันที่ใช้ `NOT EXISTS` บน block ที่ active และยังไม่หมดอายุ

## 9. การชำระเงิน งานตามเวลา และการแจ้งเตือน

**Webhook ของ gateway**
1. ตรวจลายเซ็นบน raw body
2. insert `(provider, event_id)` ใต้ unique constraint — ซ้ำ = ข้าม
3. **ดึงรายการชำระจากผู้ให้บริการด้วย ID อีกครั้ง** แล้วทำตามสถานะนั้น ไม่เชื่อ payload
4. ตอบ 200 หลัง commit เท่านั้น

- ตั้ง `expires_at` ของ QR = เวลาหมดอายุของ block − 1 นาที (Opn ตั้งรายรายการได้ — ของ Stripe ต้องยืนยันก่อนเลือก gateway)
- หน้าจ่ายเงิน: ปุ่มบันทึกรูป QR ยอดและเลขอ้างอิงเป็นข้อความ นับถอยหลัง polling สถานะ และลิงก์กลับมาทำต่อ — ถาม gateway ว่ามีการสลับไปแอปธนาคารสำหรับผู้ค้าบุคคลธรรมดาหรือไม่
- `PaymentProvider` เฟส 1 = สร้างรายการ + webhook เท่านั้น ไม่ขยายล่วงหน้าเพื่อเฟส 2
- **`EXTERNAL_TRANSFER`** (ช่วง ข ทั้งหมด และการจองที่พนักงานสร้างหลังจากนั้น): พนักงานยืนยันจากแอปธนาคารของร้าน — บังคับกรอกชื่อผู้โอนและแนบหลักฐาน ระบบบันทึกผู้ยืนยัน และรายการเหล่านี้อยู่ในรายงานกระทบยอด

**งานตามเวลา — รุ่น 1 ไม่มีตัวกวาดรายนาที**
- รายการงานประจำวันได้รายการครบกำหนด/เกินกำหนด/D+N จาก query บน `due_at` เทียบกับเวลาปัจจุบัน
- Vercel Cron วันละครั้งเรียก `/api/internal/sweep` (ป้องกันด้วย `CRON_SECRET`): สร้างงานตามวัน · เตือนกำหนดเวลา · เขียน EXPIRED ให้ PENDING_PAYMENT ที่ block หมดอายุ · hash ไฟล์ที่ยังไม่มี hash · ระบาย `domain_event` ที่ต้องส่งออก
- handler เป็น idempotent และจองแถวด้วย `FOR UPDATE SKIP LOCKED`
- **Heartbeat:** sweep เขียน `last_run_at`; ถ้าเก่ากว่า 26 ชม. ขึ้นแถบเตือนในหลังบ้านและ uptime check ภายนอกแจ้ง — กำหนดร้องทุกข์ 3 เดือนแขวนอยู่กับส่วนนี้
- เปลี่ยนเป็นรายนาทีเมื่อสร้างการแจ้งเตือนอัตโนมัติ (รุ่น 2)

**LINE และ SMS**
- ตัวรับ webhook ของ LINE OA และตาราง `line_inbound_event` สร้างในช่วง ก เพื่อเริ่มเก็บข้อความขาเข้า
- ได้ `line_user_id` ของลูกค้าสองทาง (ช่วง ค): ลูกค้าผูกเองตามหัวข้อ 10 หรือพนักงานผูก party กับผู้ส่งข้อความจาก `line_inbound_event`
- ข้อความตามขั้นตอนส่งจากปุ่มในหลังบ้าน (ช่วง ง) ผ่าน Messaging API push และเก็บลง `notification` — **ถ้ายังไม่มี `line_user_id` ปุ่มส่ง SMS ผ่าน `SmsProvider` หรือบันทึกการติดต่อด้วยมือ (โทร) ลง `notification`** เพื่อให้มีหลักฐานว่าเตือนและทวงถามเมื่อไร
- ข้อความที่พิมพ์ใน LINE OA Manager ไม่เข้าระบบ: ขั้นตอน NON_RETURN มีงาน "ส่งออกแชตจาก OA Manager แล้วแนบ"

## 10. ตัวตนและการเข้าสู่ระบบ

- **ลูกค้า: OTP ทางเบอร์โทรเท่านั้น** ในเฟส 1
  - ผู้ให้บริการ SMS ของไทยผ่าน Send SMS hook; รับเฉพาะเบอร์ +66
  - CAPTCHA ที่คำขอ OTP · จำกัดต่อเบอร์และต่อ IP · ตั้งเพดาน SMS ของโปรเจกต์อย่างตั้งใจ · session อายุยาวเพื่อไม่ให้ลูกค้าเดิมต้องขอ OTP บ่อย
- **LINE เป็นช่องทางที่ผูกกับบัญชี ไม่ใช่วิธีเข้าสู่ระบบ:** หลังเข้าสู่ระบบด้วย OTP ภายในหน้าเว็บที่เปิดใน LINE ส่ง `liff.getIDToken()` ไป `/api/v1/me/line-link` → ตรวจกับ endpoint verify ของ LINE และ channel ID → เก็บ `line_user_id` (channel สำหรับ login และ Messaging API channel อยู่ใต้ provider เดียวกันเพื่อให้ userId ตรงกัน)
  - สร้างเป็น **LINE MINI App channel** ตามคำแนะนำปัจจุบันของ LINE (ภายในยังใช้ LIFF SDK) — service message ฟรีมีเฉพาะ MINI App ที่ผ่านการยืนยัน จึงคิดต้นทุนแจ้งเตือนเป็น push ของ OA
  - LINE Login ผ่าน custom OIDC ของ Supabase ไม่น่าใช้ได้ตรง ๆ ถ้าต้องการเป็นวิธีเข้าสู่ระบบภายหลัง ให้ทำเป็น OAuth2 ธรรมดาและพิสูจน์ด้วย spike หนึ่งวันก่อน
- **พนักงาน:** อีเมล + รหัสผ่าน + TOTP; เส้นทางหลังบ้านต้องมี claim `aal2`; บัญชีเจ้าของคนแรกสร้างด้วย seed script; ไม่มีการสมัครเข้าองค์กรเอง

## 11. ความปลอดภัยของข้อมูล

- **บทบาทฐานข้อมูลสองตัวตั้งแต่ migration แรก:** `owner` (ใช้เฉพาะ migration) และ `app_runtime` (ที่ Vercel ใช้: ไม่ใช่เจ้าของตาราง ไม่มี BYPASSRLS; บน `domain_event` และ `audit_log` มีแค่ INSERT + SELECT ไม่มี TRUNCATE) + trigger `BEFORE UPDATE OR DELETE` ที่ raise บนสองตารางนี้ — ถ้าเชื่อมด้วยบทบาทเจ้าของตารางตามค่าเริ่มต้น การเพิกถอนสิทธิ์และ RLS จะไม่มีผล
- เฟส 1 ไม่พึ่ง RLS สำหรับตารางของแอป: ตารางทั้งหมดอยู่ใน schema ที่ Data API ไม่เปิด และตรวจ Security Advisor ของ Supabase
- **Storage:** runtime บน Vercel **ไม่ถือ S3 access key หรือ service_role key ของ bucket หลักฐาน** (ทั้งสองมีสิทธิ์เต็มและข้าม policy) — ออก signed URL ด้วย credential ที่จำกัดสิทธิ์ (บทบาทที่ policy บน `storage.objects` ให้เฉพาะ INSERT และ SELECT ใน bucket หลักฐาน) · key สิทธิ์เต็มอยู่เฉพาะใน secret ของงาน retention และงานสำรองข้อมูล
- **กุญแจ:** กุญแจเข้ารหัสและกุญแจ HMAC เก็บเป็น sensitive environment variable ของ Vercel หรือ cloud KMS — ไม่เก็บในฐานข้อมูล; มี `key_version` สำหรับหมุนกุญแจ
- บันทึกทุกครั้งที่พนักงานเปิดดูข้อมูลตัวตน; ลิงก์ไฟล์อายุสั้น
- Metabase (ถ้าใช้) ใช้บทบาทอ่านอย่างเดียวที่เห็นเฉพาะ schema `reporting` ไม่เห็นตารางตัวตน
- **PDPA:** ประกาศความเป็นส่วนตัว · ความยินยอมแยกสำหรับการตลาด · ความยินยอมโดยชัดแจ้งสำหรับการเทียบใบหน้า · ขั้นตอนคำขอของเจ้าของข้อมูล (30 วัน) · ขั้นตอนแจ้งเหตุละเมิด (72 ชม.) · การเก็บข้อมูลนอกประเทศ: ให้ทนายยืนยันว่าเข้าข้อยกเว้นของการเก็บบน cloud หรือไม่ ถ้าไม่ ต้องมีข้อตกลงประมวลผลข้อมูลพร้อมข้อสัญญาโอนข้อมูล

## 12. สำรองข้อมูล สภาพแวดล้อม และการทดสอบ (ช่วง ก)

**สำรองข้อมูล** — ชุดสำรองของ Supabase Pro ย้อนหลังได้จำกัด และไฟล์ใน Storage ไม่อยู่ในชุดสำรองของฐานข้อมูล
- รันเป็น scheduled workflow ของ GitHub Actions ทุกคืน: `pg_dump` (ผ่าน pooler โหมด session) ไปยัง bucket นอก Supabase เก็บ 30–90 วัน และ sync bucket หลักฐานไปผู้ให้บริการที่สองแบบมี versioning
- แต่ละงานเขียน heartbeat ที่ถูกตรวจแบบเดียวกับ sweep — แจ้งเตือนเมื่อเก่ากว่า 26 ชม.
- bucket สำรองลบเวอร์ชันเก่าและไฟล์ที่ถูกทำเครื่องหมายลบหลัง 30 วัน ให้ตรงกับการลบสองขั้นของ retention (ไม่เช่นนั้นรูปบัตรที่ลบแล้วจะค้างอยู่ในชุดสำรอง)
- ซ้อมกู้ข้อมูลหนึ่งครั้งก่อนเปิดตัว

**สภาพแวดล้อม:** โปรเจกต์ Supabase ที่สอง + โดเมน staging คงที่ + LINE channel และ key ทดสอบของ gateway ของตัวเอง (webhook และหน้าเว็บใน LINE ต้องใช้ URL คงที่ preview URL ของ Vercel ไม่พอ)

**CI:** typecheck · รัน migration บน Postgres ชั่วคราวที่มี `btree_gist` · test · build `apps/staff` แบบ static

**การทดสอบที่ต้องมี**
- table-driven test ครบทุก transition ของสถานะ
- property test: ทุกการลงบัญชีทำให้ ledger สมดุล และหนี้สินมัดจำต่อการจองกลับเป็นศูนย์เมื่อ CLOSED
- concurrency test บน Postgres จริง: ยิงการจองพร้อมกันใส่ unit เดียว และยิงการจองพร้อมกันของผู้เช่าคนเดียวใส่เพดานความเสี่ยง
- เงินเข้าหลัง block หมดอายุ และเงินเข้าหลัง unit ถูกจองต่อแล้ว
- เล่น webhook payload ที่บันทึกไว้ซ้ำสองรอบและสลับลำดับ
- browser happy path หนึ่งเส้นในโหมดทดสอบของ gateway
- test ของวันที่ข้ามเที่ยงคืนเวลาไทย และการนับวันทำการ

## 13. รายงาน

- schema `reporting` เป็น view ธรรมดา; `unit_day` = `generate_series` × units join กับ block (ที่ยกเลิกด้วยสถานะ) และเหตุการณ์สถานะ ใช้วันตามเวลาไทย — materialize เมื่อรายงานช้ากว่าราว 1 วินาทีเท่านั้น
- ชุดรายงานเปิดตัวตาม PLAN.md 3.6 ส่งมอบในช่วง ง
- ทุกแถวมี owner / operator / โหมด → รายงานผู้ปล่อยเช่าคือ query เดิมที่กรองตามเจ้าของ
- อัตราอัปโหลดล้มเหลวเก็บจากเหตุการณ์ของตั๋วอัปโหลดที่ไม่ถูก finalize

## 14. จากเว็บสู่แอป

- **ขั้น 1 แอปพนักงาน:** ห่อ static build ของ `apps/staff` ด้วย Capacitor
- **ขั้น 2 แอปลูกค้า:** Expo / React Native ใช้ `packages/domain` และ `api-client` ซ้ำ — **ตรรกะธุรกิจและ API ใช้ซ้ำ ส่วน client สร้างใหม่** (การนำทาง, การเข้าสู่ระบบ, กล้องและอัปโหลด, push, การส่งต่อไปจ่ายเงิน)
- การเช่าของจับต้องได้ไม่ใช้ in-app purchase ของ Apple (ยืนยันกับ guideline ล่าสุดตอนส่งแอป)

## 15. เฟส 2 และ 3 ในเชิงเทคนิค

- เฟส 2: UI ของผู้ปล่อยเช่าบน service เดิม; `inspection.inspector` เป็นคู่กรณีฝ่ายใดก็ได้; เพิ่มบัญชี ledger และ `fee_schedule`; **เพิ่มการตรวจความเชื่อมโยงระหว่างผู้เช่ากับผู้ปล่อยเช่า** (การตรวจระหว่างผู้เช่าด้วยกันมีตั้งแต่ช่วง ค ของเฟส 1); วิธีส่งมอบ MEETUP
- โครงสร้างเงิน B (แพลตฟอร์มเป็นคู่สัญญารับเงิน) ใช้ `PaymentProvider` เดิม กฎการลงบัญชีเลือกตามโหมด merchant of record
- **โครงสร้างเงิน A คือ integration ใหม่:** onboarding ผู้ปล่อยเช่ากับผู้ให้บริการ กติกาแบ่งจ่าย การหน่วงเงิน webhook การจ่ายออก การคืนเงินของรายการที่แบ่งจ่าย และกฎการลงบัญชีชุดที่สอง — ประเมินเมื่อผู้ให้บริการยืนยันเงื่อนไข
- เฟส 3: `custody_transfer` ชนิด INTAKE / RETURN_TO_OWNER, รหัสตำแหน่งใน `location`, ใบแจ้งยอดผู้ปล่อยเช่าจาก ledger

## 16. ต้องยืนยันกับเอกสารทางการก่อนลงมือ

รายการต่อไปนี้มาจากข้อความสรุปในผลการค้นหาหรือจากความรู้ของผู้ตรวจ ยังไม่ได้อ่านจากเอกสารทางการ

- พฤติกรรมของบทบาท Postgres บน Supabase: เจ้าของตารางข้าม RLS และคืนสิทธิ์ที่ถูกเพิกถอนให้ตัวเองได้ (หัวข้อ 11)
- S3 access key และ service_role key ของ Supabase มีสิทธิ์เต็มทุก bucket และการออก signed URL ด้วยบทบาทที่จำกัดสิทธิ์ทำได้ (หัวข้อ 11)
- ขนาด chunk 6 MB ของ TUS และเพดานขนาดไฟล์ของ Storage (หัวข้อ 8)
- request body ~4.5 MB และรอบของ Cron ต่อแพ็กเกจของ Vercel (หัวข้อ 2, 9)
- การตั้งค่า pooler / `prepare: false` (หัวข้อ 2)
- ผู้ให้บริการ SMS ที่ Supabase รองรับในตัว ค่าเริ่มต้นของเพดาน SMS และ Send SMS hook (หัวข้อ 10)
- ชุดสำรองของ Supabase Pro ย้อนหลังได้กี่วัน (หัวข้อ 12)
- Messaging API ของ LINE ไม่มีทางอ่านประวัติแชตย้อนหลัง; ข้อกำหนดของ LINE MINI App channel (หัวข้อ 9, 10)
- ID token ของ LINE web login เซ็นด้วยอัลกอริทึมใด (หัวข้อ 10)
- เวลาหมดอายุของ QR พร้อมเพย์บน Stripe และการส่งชื่อผู้โอนใน webhook ของแต่ละ gateway (หัวข้อ 9)
- static export ของ Next.js และข้อจำกัดของ Capacitor (กติกาข้อ 2)
- ขนาดไฟล์วิดีโอจริงของแต่ละวิธีจับภาพ (หัวข้อ 8 — วัดในช่วง ก)
