# แผนพัฒนาแพลตฟอร์มเช่าชุด (Rent)

> **สถานะ:** แผนฉบับร่าง 1 · 14 พ.ย. 2026 · repo ยังไม่มีโค้ด
> **ที่มาของข้อมูล:** ค้นคว้าจากเว็บ (ไทย + อังกฤษ) แล้วร่างแผน 3 มุมมองอิสระ (lean / risk-first / platform) ก่อนรวมเป็นฉบับนี้ ข้อเท็จจริงพร้อมแหล่งอ้างอิงและระดับความเชื่อมั่นอยู่ใน [research-notes.md](./research-notes.md)
> **ข้อจำกัด:** ส่วนกฎหมาย ภาษี และประกันภัย **ไม่ใช่คำแนะนำทางกฎหมาย** ต้องให้ทนายและนักบัญชีไทยตรวจก่อนใช้จริง ราคาและเงื่อนไขของผู้ให้บริการ (gateway, LINE, ขนส่ง) ต้องยืนยันกับหน้าเว็บทางการอีกครั้งก่อนเซ็นสัญญา ตัวเลขอัตรา/เกณฑ์ทั้งหมดในแผนคือ "ค่าเริ่มต้นที่ปรับได้" ไม่ใช่ค่าตายตัว

## 0. สรุปหน้าเดียว

**สิ่งที่จะสร้าง:** เว็บแอป (ใช้บนมือถือเป็นหลัก เปิดใน LINE ได้) สำหรับปล่อยเช่าชุดของตัวเอง โดยโครงสร้างข้อมูลรองรับเฟส 2–3 ตั้งแต่วันแรก แล้วค่อยต่อยอดเป็น native app เมื่อมีสัญญาณว่าคุ้ม

**แนวคิดหลัก 5 ข้อ**

1. **มัดจำอย่างเดียวกันขโมยไม่ได้** ร้านเช่าชุดไทยเก็บมัดจำราว 500–3,000 บาท ซึ่งต่ำกว่ามูลค่าชุดมาก จึงกันได้แค่คืนช้า/ของเสียหาย ระบบกันขโมยต้องเป็น 5 ชั้นทำงานร่วมกัน: ตัวตน → เงินที่วางไว้ → หลักฐาน → ช่องทางเอาคืน → การควบคุมภายใน (หัวข้อ 3.3)
2. **ชุดทุกตัวมีตัวตน และทุกครั้งที่เปลี่ยนมือมีหลักฐานสองฝ่าย** นี่คือหัวใจของทั้ง 3 เฟส สร้าง "เครื่องมือตรวจสภาพ" ตัวเดียว ใช้ซ้ำทุกเฟส (หัวข้อ 3.4)
3. **ชุดทุกตัวมี 4 บทบาทแยกกัน** — เจ้าของ / ผู้ดำเนินการ / ที่เก็บ / ผู้เป็นคู่สัญญารับเงิน เฟส 1 ทั้งสี่ค่าคือ "เรา" เฟส 2–3 แค่เปลี่ยนค่า ไม่ต้องรื้อระบบ (หัวข้อ 4.4)
4. **Super App = บริการกลาง + โมดูล, Dynamic = กฎเป็นข้อมูลที่แก้ได้** ไม่ใช่ microservices และไม่ใช่ตัวสร้างฟอร์ม/เวิร์กโฟลว์ (หัวข้อ 4.2–4.3)
5. **เริ่มปล่อยเช่าด้วยมือทันที** (LINE + สเปรดชีต + เช็กลิสต์กระดาษ) แล้วให้ซอฟต์แวร์เข้าแทนทีละส่วน ไม่รอระบบเสร็จ

**ไทม์ไลน์โดยประมาณ (นักพัฒนา 1 คน + AI ช่วยเขียนโค้ด)**

| ช่วง | ระยะเวลา | ผลลัพธ์ |
|---|---|---|
| M0 เริ่มแบบ concierge | สัปดาห์ 0–2 | ปล่อยเช่าจริงด้วยมือ 20 ครั้ง, ติดป้ายชุด, ตัดสินใจข้อ 9 |
| เฟส 1 ระบบจริง | ราว 12–13 สัปดาห์ (ตัดเหลือ 6–8 ได้ ดูหัวข้อ 7) | จอง–จ่าย–ปล่อยของ–รับคืน–คืนมัดจำ–รายงาน ครบในระบบ |
| ทดสอบตลาดเฟส 1 | จนครบ ~100 การเช่า | รู้อัตราคืนช้า/เสียหาย/หาย จริง |
| เฟส 2 | หลังผ่านเงื่อนไขก่อนเปิด (บริษัท, ทนาย, gateway) | pilot ปิด 10–20 ผู้ปล่อยเช่า → เปิดทั่วไป |
| เฟส 3 | หลังมีสถานที่เก็บ + ประกัน + สัญญาฝากเช่า | pilot 5 ราย 50 ชุด |

**5 เรื่องที่ต้องตัดสินใจก่อนเริ่มเขียนโค้ด** (รายละเอียดและค่าแนะนำอยู่หัวข้อ 9): ประเภทชุดและช่วงมูลค่า · รับที่ร้าน/ส่งพัสดุ · ช่องทางรับเงิน (gateway หรือโอนตรง+ตรวจสลิป) · จะแจ้งความจริงไหมเมื่อไม่คืน · บุคคลธรรมดาหรือบริษัท

- **"Super App"** ตีความว่า *บัญชีเดียว ระบบจ่ายเงิน/แจ้งเตือน/ยืนยันตัวตนชุดเดียว แล้วเพิ่มบริการใหม่เป็นโมดูล* (เช่น ซักแห้ง แก้ชุด ขายมือสอง เช่าเครื่องประดับ)

**สมมติฐาน (ยังไม่ได้ยืนยัน — ถ้าต่างจากนี้ ตัวเลขจะเปลี่ยน แต่โครงสร้างไม่เปลี่ยน)**
- ตลาดไทย ลูกค้าใช้ LINE / IG / TikTok / Facebook จ่ายด้วย PromptPay เป็นหลัก
- ชุดออกงาน (ราตรี ชุดไทย รับปริญญา) มูลค่าชุดละ 3,000–15,000 บาท ค่าเช่า 500–1,500 บาท
- เริ่มที่หลักสิบถึงหลักร้อยชุด มีจุดรับ–คืนชุดในกรุงเทพฯ และอาจส่งพัสดุ
- เริ่มในนามบุคคลธรรมดา มีนักพัฒนา 1 คน (หรือ AI coding ช่วย)

## 2. หลักการออกแบบ

1. **ไม่มีหลักฐาน = ไม่มีสิทธิ์เคลม ใช้กับทั้งสองฝ่าย** ทั้งร้านและผู้เช่า
2. **ทุกเกณฑ์เป็นค่าตั้งค่า** (อัตรามัดจำ ค่าปรับ กำหนดเวลา buffer) และทุกการจองต้อง snapshot ราคา + เวอร์ชันสัญญา/กติกา ณ วันที่จอง
3. **ความพร้อมให้เช่าคำนวณจากการจองและช่วงที่บล็อก ไม่ใช่จากช่องสถานะ** และฐานข้อมูลต้องกันจองซ้อนได้เอง
4. **ทุกการกระทำทางธุรกิจผ่าน API ชุดเดียว** (`/api/v1`) เพื่อให้แอปมือถือในอนาคตใช้ต่อได้ทันที
5. **สิ่งที่ห้ามตัดแม้รีบ:** ทะเบียนชุดรายตัว · หลักฐานเข้า–ออก · บันทึกการยอมรับสัญญา · สมุดบัญชีมัดจำ · ช่อง tenant และ 4 บทบาท
6. **สิ่งที่ตั้งใจไม่ทำ:** เก็บมัดจำเต็มมูลค่าทุกคน (ลูกค้าหนี) · ยึดบัตรประชาชนตัวจริง (เสี่ยงผิด พ.ร.บ.บัตรประจำตัวประชาชน ม.15 ทวิ) · เก็บเลขหลังบัตร (laser code) · ประจานคนไม่คืนชุดในที่สาธารณะ (เสี่ยงหมิ่นประมาท อาญา ม.328 + PDPA) · ค่าปรับ 2 เท่าของราคาชุด (ศาลลดได้ ป.พ.พ. ม.383) · กระเป๋าเงินเก็บมูลค่า (wallet)

## 3. เฟส 1 — ปล่อยเช่าชุดของตัวเอง

### 3.1 ขอบเขต

**ทำ**
- หน้าร้านภาษาไทย: หมวด/ชุด/รูป/ไซซ์ ปฏิทินว่าง และราคาแบบเห็นครบก่อนจอง = ค่าเช่า + มัดจำ + **มูลค่าชุดที่ตกลงกัน** + กำหนดคืน
- บัญชีผู้ใช้: OTP เบอร์โทร + LINE Login
- การจอง: เลือกวัน → ราคาถูก snapshot → ยอมรับสัญญา (เก็บเวอร์ชัน เวลา hash) → ชำระเงิน
- ยืนยันตัวตนตามระดับความเสี่ยง (3.3)
- รับเงินผ่าน PromptPay QR, สมุดบัญชีมัดจำแยกจากรายได้, คิวคืนมัดจำ
- ทะเบียนชุดรายตัว (unit) + ป้าย QR + บันทึกลักษณะเฉพาะตอนรับเข้า (intake)
- เครื่องมือตรวจสภาพ (inspection engine) + ที่เก็บหลักฐานรูป/วิดีโอ
- หลังบ้าน: กระดาน "วันนี้", ปฏิทิน, ชุด, การจอง, หน้าตั้งค่า, รายงาน, audit log
- playbook คืนช้า/ไม่คืน, เคลมความเสียหาย, บัญชีเฝ้าระวังภายใน, ชุดเอกสารหลักฐาน (evidence pack)
- แจ้งเตือนผ่าน LINE OA
- PDPA พื้นฐาน: ประกาศความเป็นส่วนตัว บันทึกความยินยอม กำหนดอายุข้อมูล

**ยังไม่ทำ (ตั้งใจ)**
native app · หน้าจอสำหรับผู้ปล่อยเช่า (มีช่องข้อมูลรอไว้ แต่ยังไม่มีหน้าจอ) · wallet · subscription · รีวิว · แชตในแอป (ใช้แชต LINE OA) · เชื่อม API ขนส่ง · RFID · **รับชำระด้วยบัตร** (ปิดในเฟส 1 — กันการจ่ายด้วยบัตรที่ขโมยมาแล้วรับมัดจำคืนเป็นเงินโอน) · ระบบนัดลองชุด (ใช้การ hold วันด้วยมือ) · ตัวสร้างฟอร์ม/หน้า/เวิร์กโฟลว์ · หลายสกุลเงิน

**ทำมือก่อน แล้วค่อยทำอัตโนมัติเมื่อถึงเกณฑ์**

| งาน | เฟส 1 ช่วงแรก | ทำอัตโนมัติเมื่อ |
|---|---|---|
| ความพร้อมให้เช่า ราคา สัญญา hash หลักฐาน | อัตโนมัติตั้งแต่แรก | — |
| ยืนยันตัวตน | ที่ร้าน: ดูบัตรตัวจริงและเก็บหลักฐานตามหัวข้อ 3.3 · ทางไกล: ยังไม่เปิด | **ก่อนเปิดส่งของทุกรูปแบบ (แมสเซนเจอร์หรือพัสดุ)** ต้องต่อ e-KYC ของผู้ให้บริการ — การตรวจรูปบัตรด้วยมือจากทางไกลไม่ปลดล็อกการส่งของ |
| คืนมัดจำ | โอนเองจากคิวคืนเงิน แนบหลักฐาน | >100 รายการ/เดือน → payout API |
| แจ้งเตือน | ระบบขึ้นรายการ พนักงานกดส่งข้อความสำเร็จรูปใน LINE OA | >30 การเช่า/เดือน หรือพลาดครั้งแรก → push อัตโนมัติ |
| ขนส่ง | จองในแอปขนส่งเอง กรอกเลขพัสดุ | >100 พัสดุ/เดือน → API (Flash / Lalamove) |
| ไล่ตามของไม่คืน | ระบบตั้งงานตามวัน คนเป็นผู้ส่งหนังสือ/แจ้งความ | >2 เคส/เดือน → สร้างหนังสืออัตโนมัติ |
| การแก้กฎที่นาน ๆ แก้ที | แก้แถวข้อมูลโดยตรง | กฎไหนถูกแก้ >2 ครั้ง/เดือน → สร้างหน้าจอ |

### 3.2 เส้นทางผู้ใช้

**ผู้เช่า:** เข้าจาก LINE rich menu / ลิงก์ IG → เลือกชุดและวัน → เห็นราคาครบ (ค่าเช่า มัดจำ มูลค่าชุด วันคืน) → เข้าสู่ระบบด้วย OTP → ยืนยันตัวตนตามระดับที่ต้องใช้ + ให้เลขบัญชีรับเงินคืน (ระบบตรวจว่าชื่อบัญชีตรงกับบัตรก่อนยืนยันการจอง) → ยอมรับสัญญา → สแกนจ่าย → รับชุดและกดรับทราบรายงานสภาพ → คืนชุดตามกำหนด → ได้มัดจำคืนหรือได้ใบแจ้งหักแบบแจกแจงรายการ

**เจ้าของ/พนักงาน:** รับชุดเข้าระบบ (ติดป้าย ถ่ายรูป วัด ชั่ง ตั้งมูลค่า) → ตั้งกติกาต่อหมวด → ทำงานจากกระดาน "วันนี้": แพ็ก · ส่งมอบ · ครบกำหนดคืน · เกินกำหนด · ตรวจรับ · คืนมัดจำ — **ทุกการกระทำกับชุดเริ่มจากสแกน QR ของชุด**

### 3.3 ระบบป้องกันชุดหาย/ถูกขโมย

#### ชั้นที่ 1 — ตัวตน: รู้ว่าใครถือชุดอยู่

ระดับความน่าเชื่อถือของผู้เช่า

| ระดับ | เงื่อนไข |
|---|---|
| **T0 ใหม่** | OTP เบอร์โทร (+ LINE) เท่านั้น |
| **T1 ยืนยันแล้ว** | e-KYC (OCR บัตร + liveness + เทียบใบหน้า; ผู้ให้บริการไทยราว 3–5 บาท/ครั้ง) **หรือ** ตรวจที่หน้าร้านแบบมีหลักฐาน (พนักงานดูบัตรตัวจริงแล้วคืน + ถ่ายรูปบัตรแบบปิดทับศาสนา/หมู่เลือด + รูปตอนส่งมอบที่เห็นผู้เช่าถือชุด) **และ** บัญชีรับเงินคืนที่ตรวจแล้วว่าชื่อตรงกับบัตร (โอน 1 บาท หรือ API ตรวจชื่อบัญชี) |
| **T2 ลูกค้าประจำ** | T1 + บัญชีอายุ ≥30 วัน + คืนเรียบร้อย ≥2 ครั้งใน 12 เดือน ไม่มีเคลมที่ถูกตัดสินว่าผิด ไม่เคยช้าเกิน 24 ชม. |
| **จำกัดสิทธิ์** | ตรงกับบัญชีเฝ้าระวังภายใน (hash ของเลขบัตร เบอร์โทร บัญชีธนาคาร ที่อยู่ อุปกรณ์) |

กติกาที่ใช้กับทุกระดับ
- **ไม่ยืนยันตัวตน = ไม่ได้รับชุด ทุกกรณี** แม้วางมัดจำเต็มมูลค่า เพราะเงินมัดจำอาจไม่ใช่เงินของผู้เช่าเอง (ดู "โอนสามเส้า" ในตารางภัยคุกคาม)
- **การตรวจรูปบัตร + เซลฟีด้วยมือจากทางไกลไม่ถือเป็น T1** — ไม่มีการตรวจว่าเป็นคนจริง และชุดรูปบัตร + เซลฟีมีขายพร้อมบัญชีม้า การยืนยันทางไกลต้องเป็น e-KYC เท่านั้น
- **ทุกเส้นทางต้องได้เลขบัตร 13 หลักและที่อยู่ตามบัตร** เพราะบัญชีเฝ้าระวัง หนังสือทวงถาม และการแจ้งความล้วนต้องใช้ — "ติ๊กว่าดูบัตรแล้ว" อย่างเดียวไม่พอ
- **เก็บวันเกิดจากบัตร:** ผู้เช่าอายุต่ำกว่า 20 ปี → มัดจำ 100% ของมูลค่าชุดทุกระดับ หรือให้ผู้ปกครองเป็นคู่สัญญา (ลูกค้าเลือก) และไม่พึ่งการเรียกเก็บเงินย้อนหลังกับกลุ่มนี้ (ให้ทนายยืนยัน)

ข้อปฏิบัติด้านข้อมูลส่วนบุคคล: ขอความยินยอมโดยชัดแจ้งแยกหน้าจอสำหรับการเทียบใบหน้า (ข้อมูลชีวภาพ) · เก็บผลการตรวจ + ชื่อ/เลขบัตร/ที่อยู่แบบเข้ารหัส + keyed hash สำหรับตรวจซ้ำ · รูปบัตร (ปิดทับศาสนา/หมู่เลือด) และรูปตอนส่งมอบ เก็บแบบเข้ารหัสจนการจองปิดและพ้นช่วงเคลม แล้วลบอัตโนมัติ — หยุดนับเมื่อมีข้อพิพาทหรือคดี · บันทึกทุกครั้งที่พนักงานเปิดดูข้อมูลบัตร

#### ชั้นที่ 2 — เงินที่วางไว้: มัดจำตามความเสี่ยง

แบ่งชุดตาม **มูลค่าที่ตกลงกัน** (ประกาศก่อนจอง): **A** ≤3,000 บาท · **B** 3,001–10,000 · **C** >10,000

มัดจำ = มูลค่าชุด × อัตรา และไม่ต่ำกว่า 1 เท่าของค่าเช่า (ค่าเริ่มต้น ปรับได้ทั้งตาราง)

| | Band A | Band B | Band C |
|---|---|---|---|
| **T0** | จองแบบรับที่ร้านได้ — ตรวจตัวตนที่เคาน์เตอร์ก่อนรับชุด (เป็น T1 ทันที) แล้วใช้อัตรา T1 | เหมือน Band A | ไม่อนุญาต |
| **T1** | 30% | 30%; ส่งพัสดุได้เมื่อซื้อความคุ้มครองตามมูลค่า | 50%; รับที่ร้านหรือร้านไปส่งเองพร้อมดูบัตร; เช่าได้ทีละ 1 ชุด |
| **T2** | 20% | 20% | 30%; เงื่อนไขการรับ–ส่งเหมือน T1 |
| **จำกัดสิทธิ์** | รับที่ร้านเท่านั้น มัดจำ 100% หรือปฏิเสธ | | |

ตัวอย่าง: ชุดมูลค่า 6,000 บาท ค่าเช่า 900 บาท/4 วัน → T1 มัดจำ 1,800 บาท, T2 มัดจำ 1,200 บาท (อยู่ในช่วงที่ร้านไทยเก็บกันคือ 1–2 เท่าของค่าเช่า) ส่วนต่างอีก 4,200 บาทคุ้มครองด้วยชั้น 1, 3 และ 4

**เพดานความเสี่ยงรวม** — ตารางข้างบนคิดทีละการจอง จึงต้องมีเพดานรวม กันคนเช่าหลายชุดพร้อมกันแล้วหายไป (ระบบตรวจตอนยืนยันการจอง)
- **วงเงินที่ยังไม่ถูกคุ้มครองต่อผู้เช่า** = ผลรวมของ (มูลค่าชุด − มัดจำ) ของทุกการจองที่ยังเปิดอยู่: T1 ไม่เกิน 6,000 บาท, T2 ไม่เกิน 12,000 บาท — ส่วนที่เกินต้องวางมัดจำ 100%
- **นับรวม "กลุ่มที่เชื่อมโยงกัน"** — บัญชีที่ใช้ที่อยู่ อุปกรณ์ บัญชีรับเงินคืน หรือผู้จ่ายเงินเดียวกัน ถือเป็นผู้เช่ารายเดียว
- **อัตรา T2 ใช้ได้ถึง band สูงสุดที่เคยเช่าและคืนเรียบร้อยแล้วเท่านั้น** (คืนชุดราคาถูกสองครั้งไม่ได้สิทธิ์ลดมัดจำชุดแพง) และการส่งของไปที่อยู่ใหม่ครั้งแรกคิดอัตรา T1
- **เพดานทั้งร้าน** สำหรับวงเงินที่ยังไม่ถูกคุ้มครองของบัญชีอายุน้อยกว่า 60 วันรวมกัน (กันการกวาดชุดช่วงเทศกาล)

ข้อเท็จจริงที่กำหนดการออกแบบ: PromptPay "กันวงเงิน" ไม่ได้ มัดจำจึงเป็นเงินที่รับเข้าจริงและต้องโอนคืน · การกันวงเงินบัตรอยู่ได้ราว 5–7 วัน จึงไม่พอสำหรับรอบเช่าที่มีขนส่ง → **ค่าเริ่มต้นคือ "เก็บจริงแล้วคืน"** พร้อมสัญญาระดับบริการ: คืนมัดจำภายใน 24 ชม. หลังตรวจผ่าน (ช้าสุด 3 วันทำการ)

#### ชั้นที่ 3 — หลักฐานและการกันสลับชุด

- **ป้ายประจำตัวต่อชุด (ไม่ใช่ต่อแบบ):** ป้ายผ้าเย็บติดด้านใน มีเลขซีเรียล + QR (รหัสสุ่ม ไม่บอกข้อมูล) ต้นทุนหลักหน่วยบาท
- **เครื่องหมายลับชั้นที่สอง:** หมึก UV หรือป้ายเย็บซ่อนในตะเข็บ ตำแหน่งบันทึกไว้เฉพาะหลังบ้าน — ชุดปลอมที่ย้ายป้าย QR มาติดจะไม่ผ่าน
- **ลายนิ้วมือของชุด (ตอน intake):** รูปมาโครของป้าย ตะเข็บ ซับใน ตำหนิเดิม · น้ำหนักเป็นกรัม · ขนาดวัดราบ (±1 ซม.)
- **ตอนรับคืน ต้องผ่าน QR + เครื่องหมายลับ + น้ำหนัก ก่อนปล่อยมัดจำทุกครั้ง** และชุด Band B/C ต้องเทียบรูปมาโครของจุดธรรมชาติ 2 จุด (ตะเข็บป้ายยี่ห้อ + ตะเข็บอีกหนึ่งจุด) กับรูปตอน intake ด้วย — เพราะป้ายเลาะแล้วเย็บใหม่ได้ หมึก UV หาเจอและเลียนแบบได้ และน้ำหนักแยกชุดรุ่นเดียวกันไม่ออก
- **เครื่องหมายลับตรวจหลังบ้าน ไม่ตรวจต่อหน้าผู้เช่า** และมีเครื่องหมายสำรองอีกหนึ่งจุดที่ไม่ตรวจเป็นประจำ (ใช้เมื่อสงสัย หรือเมื่อเจ้าของสุ่มตรวจ)
- **ทดสอบเครื่องหมายกับร้านซักแห้งที่ใช้จริงก่อน M2** — ถ้าหมึก UV ไม่ทนน้ำยาซัก ให้ใช้ป้าย NFC แบบเย็บติดสำหรับงานซักแทน
- **สัญญาต้องระบุ:** หากพบว่าไม่ใช่ชุดตัวจริงภายในช่วงตรวจรับ ให้ถือเป็นการไม่คืนชุด แม้กดรับคืนที่เคาน์เตอร์ไปแล้ว
- **สัญญาอิเล็กทรอนิกส์:** กดยอมรับในเซสชันที่ยืนยัน OTP เก็บเวอร์ชันสัญญา เวลา และ hash (พ.ร.บ.ธุรกรรมทางอิเล็กทรอนิกส์ ม.7–9 รองรับ — ให้ทนายยืนยันถ้อยคำ)
- **การจองยืนยันได้จากสัญญาณการรับเงินจริงเท่านั้น** (webhook ของ gateway หรือผลตรวจสลิปผ่าน API) ไม่ใช่รูปสลิปที่ลูกค้าส่งมา
- **เงินต้องมาจากผู้เช่าเอง:** เก็บชื่อผู้โอนเมื่อผู้ให้บริการส่งมาให้ (API ตรวจสลิปมี; gateway ต้องสอบถาม) ถ้าไม่ตรงกับชื่อผู้เช่า ให้ขึ้นธงให้คนตรวจก่อนส่งมอบ — ไม่บล็อกอัตโนมัติ เพราะพ่อแม่จ่ายแทนเป็นเรื่องปกติ
- **เงินคืนกลับทางเดิม:** คืนเข้าบัญชีที่โอนมาเมื่อรู้บัญชี; คืนเข้าบัญชีอื่นได้เฉพาะเมื่อชื่อผู้โอนตรงกับชื่อผู้เช่า นอกนั้นให้เจ้าของตรวจ; เงินคืนจากการยกเลิกของลูกค้าใหม่ คืนหลัง 7 วันหรือเป็นเครดิต
- RFID ยังไม่จำเป็นที่ขนาดนี้ ค่อยพิจารณาตอนเฟส 3 เมื่อมีคลังหลายร้อยชุด

#### ชั้นที่ 4 — ช่องทางเอาคืน: playbook เมื่อไม่คืนชุด

เงื่อนไขสัญญาที่ออกแบบให้ทนต่อการถูกโต้แย้งว่าไม่เป็นธรรม: ประกาศมูลค่าชุดก่อนจอง · ค่าปรับคืนช้าต่อวัน = ค่าที่มากกว่าระหว่าง 2 เท่าของค่าเช่าต่อวัน กับ 300 บาท (คืนช้าต้องแพงกว่าเช่าต่อ ไม่เช่นนั้นคนจะจองสั้นแล้วถือยาว) บวกค่าเสียหายจริงที่มีหลักฐานหากทำให้การจองถัดไปเสีย **รวมแล้วไม่เกินมูลค่าชุด** · ค่าซ่อม/ซักคิดตามจริงพร้อมรูปและใบเสร็จ · สึกหรอตามปกติไม่คิด · ชุดหาย/เสียทั้งตัวคิด "มูลค่าที่ตกลงหักค่าเสื่อม" ไม่ใช่ราคาป้าย โดยค่าเสื่อมผูกกับเกรดสภาพ (ชุดเกรด A/B คิดไม่ต่ำกว่า 60% ของมูลค่าตั้งต้น) เพื่อไม่ให้ชุดขายดีถูก "ซื้อ" ได้ในราคามัดจำ — ระดับค่าปรับและค่าเสื่อมให้ทนายตรวจพร้อมสัญญา

ระบบตั้งงานอัตโนมัติตามวัน (D = วันครบกำหนดคืน)

| วัน | สิ่งที่เกิดขึ้น |
|---|---|
| D−1, D | เตือนผ่าน LINE |
| D+1 | เริ่มคิดค่าปรับรายวัน + โทรตาม; ถ้าไม่มีสแกนส่งคืนภายใน 12:00 ระบบเตือนว่าการจองถัดไปของชุดนี้เสี่ยง |
| D+3 | หนังสือทวงถามทาง LINE และไปรษณีย์ลงทะเบียนตามที่อยู่ในบัตร |
| D+7 | สถานะ **NON_RETURN**: หักมัดจำ ออกใบแจ้งหนี้มูลค่าชุดหักค่าเสื่อม ขึ้นบัญชีเฝ้าระวังภายใน สร้าง evidence pack |
| D+30 | แจ้งความร้องทุกข์ — ยักยอก (อาญา ม.352) หรือฉ้อโกง (ม.341) หากใช้ตัวตนปลอมตั้งแต่ต้น |
| D+60 | สัญญาณเตือนขั้นเด็ดขาด: ความผิดยอมความได้ ต้องร้องทุกข์ **ภายใน 3 เดือน** นับแต่รู้เรื่องและรู้ตัวผู้กระทำ (ม.96) |

**Evidence pack (กดครั้งเดียวได้ PDF + รายการไฟล์พร้อม hash):** สัญญาและบันทึกการยอมรับ · ผลยืนยันตัวตน · หลักฐานการชำระ · รายงานและสื่อตอนปล่อยของ · เหตุการณ์จากขนส่ง · ประวัติแชต LINE · หนังสือทวงถามและหลักฐานการส่ง · มูลค่าชุด — ตำรวจมักมองการคืนช้าเฉย ๆ เป็นเรื่องแพ่ง เอกสารจึงต้องชี้ "เจตนาทุจริต" (หลบเลี่ยง ตัวตนปลอม นำไปขายต่อ)

คดีแพ่ง: ผู้ให้เช่าต้องฟ้องภายใน 6 เดือนนับแต่วันคืนทรัพย์ (ป.พ.พ. ม.563) และสำหรับชุดราคาหลักพันถึงหมื่นมักไม่คุ้มค่าใช้จ่าย — มัดจำ + การร้องทุกข์คือเครื่องมือหลักในทางปฏิบัติ

#### ชั้นที่ 5 — การควบคุมภายใน

บัญชีพนักงานรายบุคคล + MFA · คืนเงินได้เฉพาะบัญชีที่ชื่อตรงกับผู้เช่า · การตัดจำหน่าย/ยกเว้นค่าปรับต้องให้เจ้าของอนุมัติ · นับสต็อกด้วยการสแกนทุกสัปดาห์ · event log แก้ไข/ลบไม่ได้ · รายงานการ override รายคน · กล้องวงจรปิดที่จุดแพ็ก/รับคืน

เมื่อมีพนักงานที่ไม่ใช่เจ้าของ ให้เพิ่ม: เจ้าของกระทบยอดเงินคืนที่โอนออกกับรายการเดินบัญชีธนาคาร (หรือให้สลิปโอนออกผ่าน API ตรวจสลิปว่าชื่อผู้รับและยอดตรงกับรายการคืนเงิน — สลิปที่พนักงานแนบเองเชื่อได้ไม่มากกว่าสลิปของลูกค้า) · เจ้าของสุ่มตรวจชุดจำนวนหนึ่งทุกเดือนด้วยรูปมาโครและเครื่องหมายลับ ไม่ใช่ด้วย QR · สุ่มตรวจซ้ำ 10% ของผล "ผ่าน" ของชุด Band B/C ก่อนปล่อยมัดจำ

### 3.4 ขั้นตอนปล่อยของออก – รับของเข้า (check-out / check-in)

เครื่องมือเดียวทำทุกการตรวจ โดยเช็กลิสต์มาจากแม่แบบของแต่ละหมวดชุด (แก้ได้จากหลังบ้าน) **ให้ลองทำบนกระดาษกับการเช่าจริง 20 ครั้งแรกและจับเวลา เป้าหมายไม่เกิน 5 นาทีต่อครั้ง**

**หลักฐานที่เก็บทุกครั้ง**
- ชุดรูปตามลำดับที่ระบบนำ: หน้า หลัง ซับใน ชายกระโปรง ใต้วงแขน ซิป ป้าย+QR อุปกรณ์เสริมทุกชิ้น ตำหนิเดิมทุกจุด
- วิดีโอต่อเนื่อง 20–30 วินาที **เริ่มที่ป้าย QR และเลขการจอง**
- ติ๊กรายการชิ้นส่วน (ชุด เข็มขัด ซับ ผ้าคลุม ถุงคลุม ไม้แขวน) · น้ำหนัก · เกรดสภาพ A–D (X = ให้เช่าไม่ได้)
- ทุกไฟล์: เวลาเซิร์ฟเวอร์ ผู้อัปโหลด และ SHA-256 บันทึกลง event log; เก็บใน bucket ส่วนตัวที่บทบาทแอปลบไม่ได้
- หมายเหตุ: หน้าเว็บบังคับ "ถ่ายสดเท่านั้น" ไม่ได้ 100% ความน่าเชื่อถือจึงมาจากวิดีโอที่ขึ้นต้นด้วย QR + เลขจอง เวลาเซิร์ฟเวอร์ hash และการรับทราบของอีกฝ่าย

**ปล่อยของ — รับที่ร้าน**
1. เปิดการจองจากกระดาน "วันนี้" สแกน QR ชุด — ระบบไม่ให้ไปต่อถ้าการจ่ายเงิน ตัวตน หรือสัญญายังไม่ครบ
2. ถ่ายตามเช็กลิสต์ (หรือใช้ชุดรูปตอนแพ็กที่อายุไม่เกิน 24 ชม.)
3. ดูบัตรตัวจริงเทียบกับชื่อผู้จอง แล้วคืนบัตร
4. ผู้เช่าอ่านรายงานสภาพบนมือถือตัวเองและกดรับทราบ → การจองเป็น ACTIVE — บันทึกสภาพที่ทั้งสองฝ่ายรับรู้ทำให้ทั้งตำหนิเดิมและความเสียหายใหม่พิสูจน์ได้ (ป.พ.พ. ม.561 สันนิษฐานว่าผู้เช่ารับของในสภาพดีหากไม่มีบันทึก — ให้ทนายยืนยันถ้อยคำ)

**ปล่อยของ — ส่งพัสดุ**
1. ที่จุดแพ็กประจำ: ชุดรูป + วิดีโอต่อเนื่องแสดงป้าย QR ชิ้นส่วน การใส่ถุงกันแกะที่มีเลขกำกับ น้ำหนักกล่องบนตาชั่ง และใบปะหน้า
2. ส่งในบัญชีของร้าน ซื้อความคุ้มครองตามมูลค่าเมื่อชุดเกิน ~2,000 บาท ใส่ถุง/ซีล/ใบปะหน้าสำหรับส่งคืนไว้ในกล่อง
3. สแกนรับพัสดุของขนส่ง → OUT; สแกนส่งสำเร็จ → DELIVERED
4. ผู้เช่ามีเวลา 24 ชม. (หรือถึง 20:00 วันเดียวกัน สำหรับงานวันรุ่งขึ้น) แจ้งปัญหาผ่านหน้าการจอง **เงียบ = ยอมรับ** — การแจ้งต้องเป็น **คลิปต่อเนื่องคลิปเดียว เริ่มจากซีลขาออกที่ยังสมบูรณ์และเห็นเลขซีล ไปจนถึงตำหนิ** คลิปแบบอื่นบันทึกเป็น "รับทราบ แต่ไม่ถือเป็นหลักฐาน"
5. ชุดที่ส่งทางพัสดุติด **ป้ายกันใส่** ขนาดใหญ่มีเลขกำกับไว้ด้านนอก ("ตัดป้าย = ยอมรับสภาพชุด") — ขอคืนเงินหรือเปลี่ยนชุดได้เมื่อป้ายยังอยู่เท่านั้น กันการใส่ไปแล้วอ้างว่าได้รับมาเสียหาย
6. ผลของการแจ้งปัญหา: ตำหนิที่ร้านยอมรับและผู้เช่าใช้ชุดต่อ → บันทึกเป็นตำหนิเดิม ไม่คิดเงินผู้เช่า · ชุดใส่ไม่ได้ → ป้ายกันใส่ยังอยู่ ส่งกลับภายใน 24 ชม. คืนเงินเต็ม

**รับของเข้า — คืนที่ร้าน**
1. ต่อหน้าผู้เช่า: สแกน QR → น้ำหนัก → นับชิ้นส่วน → ดูสภาพที่เห็นได้ โดยระบบแสดงรูปตอนปล่อยของเทียบข้างกัน ทั้งสองฝ่ายกดรับทราบ — **การกดรับทราบที่เคาน์เตอร์หมายถึง "รับคืนชุดเลขนี้ ครบกี่ชิ้น" เท่านั้น ไม่ใช่การรับรองสภาพ**
2. ตรวจละเอียดหลังบ้านภายในช่วงตรวจรับ (รวมเครื่องหมายลับและรูปมาโคร) — สิทธิ์เคลมสภาพยังอยู่ตลอดช่วงตรวจรับ และสัญญาต้องระบุข้อนี้ไว้

**รับของเข้า — คืนทางพัสดุ**
1. ก่อนส่ง ผู้เช่าอัปโหลด **คลิปแพ็กต่อเนื่อง**: ป้าย QR → ใส่ชุดลงถุง → เลขซีล → ใบปะหน้า — ไม่มีคลิปนี้ โต้แย้งวิดีโอแกะกล่องของร้านไม่ได้
2. ผู้เช่าส่งถุงที่ซีลแล้วให้ขนส่งภายในวันครบกำหนด **สแกนรับพัสดุครั้งแรกของขนส่งหยุดนับค่าปรับคืนช้าเท่านั้น** — ความรับผิดชอบต่อของในกล่องสิ้นสุดเมื่อร้านเปิดกล่องที่ซีลสมบูรณ์และตรวจตัวตนชุดผ่าน
3. ระบบบันทึกน้ำหนักที่ขนส่งรับ เทียบกับน้ำหนักขาออก — ต่างกันเกินเกณฑ์ ให้เปิดเคสอัตโนมัติ
4. ที่จุดรับประจำ: วิดีโอต่อเนื่อง — เลขซีล ชั่งกล่อง แกะ สแกน QR ตรวจ UV ชิ้นส่วน แล้วถ่ายตามเช็กลิสต์
5. ตัดสิน **ผ่าน**, **ผ่านแบบกันเงินไว้ก่อน** หรือ **เคลม** ภายใน 48 ชม. นับจากพนักงานสแกนรับ

**หลังตรวจ**
- **ผ่าน:** เข้าคิวคืนมัดจำ → โอนเข้าบัญชีที่ชื่อตรงกับผู้เช่า; ชุดไปสถานะ CLEANING
- **ผ่านแบบกันเงินไว้ก่อน:** เมื่อพบคราบหรือกลิ่นที่ยังไม่รู้ว่าซักออกหรือไม่ — กันเงินเท่ากับค่าเสียหายระดับ "ถาวร" ตามตารางไว้จนรู้ผลจากร้านซัก (ไม่เกิน 5 วันทำการ) และคืนส่วนที่เหลือภายใน 24 ชม.
- **เคลม:** ส่งใบแจ้งแบบแจกแจง (รูป + บรรทัดจากตารางค่าซ่อม) ผู้เช่ามี 48 ชม. โต้แย้ง เจ้าของตัดสิน; เคลมเกิน 1,000 บาทต้องเจ้าของอนุมัติ; มัดจำส่วนที่ไม่มีข้อโต้แย้งคืนภายใน 24 ชม.

**บันทึกความเสียหาย** = ประเภท (คราบ กลิ่น ขาด/ตะเข็บปริ เกี่ยว ไหม้ ลูกปัด/กระดุมหาย ซิปเสีย โครงเสีย สีตก ดัดแปลงโดยไม่อนุญาต ซักเองจนเสียหาย ชิ้นส่วนหาย ขึ้นรา) × ตำแหน่ง × ความรุนแรง 1–4 (ซักออก / ซ่อมได้ / ถาวร / เสียทั้งตัว) × ที่มา (เดิม / ผู้เช่า / ขนส่ง / ร้านซัก / ไม่ทราบ)

### 3.5 ปฏิทินและช่วงกันชน

- ช่วงที่ชุดถูกบล็อกต่อ 1 การจอง = เตรียมของ + ขนส่งขาไป + วันเช่า + ขนส่งขากลับ + ตรวจ + ซัก + กันชน 1 วัน — แต่ละค่าตั้งได้ตามหมวด วิธีส่ง และโซน
- ค่าเริ่มต้น (ตั้งเผื่อไว้ก่อน แล้วลดจากข้อมูลจริง): รับเองในกรุงเทพฯ ~7–8 วัน, ส่งต่างจังหวัด ~13 วัน → ชุดหนึ่งหมุนได้ราว 2–4 รอบ/เดือน
- ระยะเช่ามาตรฐานเริ่มที่ 4 วัน (รวมวันรับและวันคืน) ยึดกับวันงานของลูกค้า
- เมื่อคืนช้าและกระทบการจองถัดไป: หาชุดทดแทน/อัปเกรด → ส่งแมสเซนเจอร์ไปรับคืนวันเดียวกัน → คืนเงิน + เครดิต
- การลองชุด: ในเฟส 1 พนักงาน hold วันด้วยมือ (ประเภทบล็อก `HOLD`)

### 3.6 สถิติและรายงาน ("รายงานทุกอย่าง")

**หลักการ: เก็บทุกข้อเท็จจริงตั้งแต่วันแรก แล้วค่อยสร้างหน้ารายงานเมื่อมีคำถามจริง** — "รายงานได้ทุกอย่าง" เกิดจากการไม่ทำข้อมูลหาย ไม่ใช่จากการสร้าง 50 dashboard ล่วงหน้า กฎ: ถ้าตัวชี้วัดไหนคำนวณจาก event ไม่ได้ ให้เพิ่ม event ที่ขาด ไม่ใช่ปะที่รายงาน

**สิ่งที่ถูกบันทึก:** ทุกการเปลี่ยนสถานะ (ใคร เมื่อไร ที่ไหน หลักฐานอะไร) · ทุกบาทในสมุดบัญชีคู่ · รายละเอียดราคาของแต่ละการจอง · เกรดและความเสียหายจากการตรวจ · ข้อความที่ส่ง · การแก้ค่าตั้งค่า · การ override และการเปิดดูข้อมูลบัตรของพนักงาน · ช่องทางที่ลูกค้ามา · ต้นทุนซื้อ/ซัก/ซ่อมต่อชุด · funnel หน้าร้าน

| ต่อชุด | อัตราการใช้งาน (วันที่ถูกเช่า ÷ วันที่พร้อมให้เช่า) · รายได้ ต้นทุน และกำไรต่อชุด · จำนวนครั้งเช่าจนคืนทุน · วันที่ไม่ถูกเช่า (60/90 วัน) · แนวโน้มเกรดสภาพ |
| การเงิน | ยอดเช่ารวม · รายได้สุทธิ · มัดจำคงค้าง · เวลาคืนมัดจำเทียบเป้า 24 ชม. · ค่าธรรมเนียมรับเงิน · กำไรส่วนเกินต่อการเช่า |
| ปฏิบัติการ | เวลาหมุนรอบ (รับคืน → พร้อมเช่า) แยกตามขั้น · เวลาที่ใช้ตรวจ · ความครบของหลักฐาน · วันที่บล็อกจริงเทียบแผน · ค่าซัก |
| ความเสี่ยง | อัตราคืนช้า / ไม่คืน แยกตามระดับผู้เช่าและ band · อัตราเสียหายตามประเภท · อัตราเคลมที่เก็บได้ · มูลค่าที่เสี่ยง (มูลค่าชุดที่ออกไป − มัดจำที่ถือ) · อัตราความสูญเสียต่อรายได้ · อัตราพัสดุหาย · ผลต่างนับสต็อก |
| ลูกค้า | funnel ดู → จ่าย · อัตราหลุดที่ขั้น KYC และขั้นมัดจำ (ราคาของความยุ่งยาก) · ยกเลิก · กลับมาเช่าซ้ำ · ช่องทางที่มา · รายได้ตามหมวด |

**วิธีผลิตรายงาน**
- schema `reporting` แบบอ่านอย่างเดียว: SQL view + materialized view รวมตาราง `unit_day` (1 แถวต่อชุดต่อวัน) ที่เป็นตัวหารของอัตราการใช้งาน
- dashboard ในแอปสำหรับตัวเลขประจำวัน + ส่งออก CSV ทุกรายงาน
- Metabase (โอเพนซอร์ส ติดตั้งเอง) สำหรับคำถามเฉพาะกิจ — เพิ่มเมื่อมีคำถามที่ view เดิมตอบไม่ได้เป็นประจำ
- PostHog สำหรับ funnel หน้าร้าน
- ทุกแถวมีเจ้าของ/ผู้ดำเนินการ/โหมด → รายงานสำหรับผู้ปล่อยเช่าในเฟส 2–3 คือ query เดิมที่กรองตามเจ้าของ

### 4.2 "Super App" = บริการกลาง + โมดูล ในระบบเดียว

Super app ของจริง (LINE, Grab, WeChat) คือ "เปลือกหลัก + บริการกลางร่วม" แล้วให้ mini-app ใช้บริการกลางผ่านสัญญาที่ชัดเจน บทเรียนที่ควรเอามาคือ **บริการกลางกับสัญญาระหว่างโมดูล** ไม่ใช่การแยกระบบเป็นหลายเซิร์ฟเวอร์

**รูปแบบ: modular monolith** — repo เดียว deploy เดียว ฐานข้อมูลเดียว

- **`core` (ทุกบริการในอนาคตใช้ร่วม):** ตัวตนและองค์กร · KYC และระดับความน่าเชื่อถือ · สัญญา/การยอมรับ · การชำระเงินและสมุดบัญชี · สื่อและเครื่องมือตรวจสภาพ · เคส/ข้อพิพาท · การขนส่ง · แจ้งเตือน · ค่าตั้งค่าและ feature flag · event/audit log · ตัวจับเวลา · ภาษา (ไทย/อังกฤษ)
- **โมดูล:** `rental` (เฟส 1) · `marketplace` (เฟส 2) · `managed` (เฟส 3) · บริการถัดไป (ซักแห้ง แก้ชุด ขายมือสอง ฯลฯ)
- **ทะเบียนโมดูล:** แต่ละโมดูลประกาศ manifest — เส้นทาง เมนูตามบทบาท สิทธิ์ schema ของค่าตั้งค่า event บัญชีในสมุดบัญชี แม่แบบข้อความ; เปลือกหลักสร้างเมนูจาก manifest + flag เปิด/ปิดต่อองค์กร
- **ขอบเขต:** โมดูลคุยกันผ่านอินเทอร์เฟซที่ export หรือ domain event (ตาราง outbox) เท่านั้น ห้าม import ข้ามกัน; แยก Postgres schema ต่อโมดูล
- **การชำระเงินอ้างสิ่งที่ถูกจ่ายเป็น `(module, ref_type, ref_id)`** ไม่ใช่ foreign key ไปที่ `booking` — บริการใหม่เก็บเงินได้โดยไม่แตะตารางของ rental
- โมดูล `rental` ให้เช่า "ของจับต้องได้" — ความเป็นเสื้อผ้าอยู่ในค่าตั้งค่าของหมวด จึงขยายไปเช่าของอย่างอื่นได้

### 4.3 "ไดนามิก" = ข้อมูลที่มีเวอร์ชันและวันที่มีผล ไม่ใช่ตัวสร้างระบบ

**เป็นข้อมูล แก้ได้โดยไม่แก้โค้ด**

| เรื่อง | รูปแบบ |
|---|---|
| หมวดชุดและคุณสมบัติ | JSON Schema ต่อหมวด ค่าเก็บใน JSONB (ตรวจด้วย `pg_jsonschema`); ฟิลด์ที่ใช้กรอง/รายงาน (ไซซ์ สี มูลค่า ต้นทุน) ยกเป็นคอลัมน์จริง |
| ราคา | แถวกฎตามขอบเขต (องค์กร → หมวด → ชุด) มีลำดับความสำคัญและช่วงวันที่: ขั้นตามจำนวนวัน ตัวคูณวันหยุด/ฤดูกาล — ประเมินด้วยฟังก์ชันเดียว และ snapshot ผลลงการจอง |
| มัดจำ ค่าปรับ ตารางค่าซ่อม/ซัก | แถวกฎแบบเดียวกัน |
| ตารางความเสี่ยง (ระดับ × band) เกณฑ์เลื่อนระดับ ตัวจับเวลา ช่วงกันชนปฏิทิน | `policy_profile` มีเวอร์ชัน |
| เช็กลิสต์ตรวจสภาพ | แม่แบบมีเวอร์ชันต่อหมวด (ผ่าน/ไม่ผ่าน เกรด มุมรูปที่บังคับ จำนวนชิ้นส่วน) |
| สัญญาเช่าและนโยบาย | มีเวอร์ชัน + บันทึกการยอมรับ |
| เนื้อหาหน้าร้าน ข้อความแจ้งเตือน | ตารางเนื้อหา / แม่แบบข้อความ |
| เปิด/ปิดฟีเจอร์ บทบาทผู้ใช้ | flag ต่อองค์กร; บทบาทเป็นข้อมูล |
| ตารางค่าคอมมิชชัน (เฟส 2–3) | `fee_schedule` — เฟส 1 ตั้งไว้ 0% |

**อยู่ในโค้ดโดยเจตนา:** state machine ของชุดและการจอง · รายการสิทธิ์ · กฎการลงบัญชี

**กับดักที่จะไม่ทำ:** ตัวสร้างฟอร์ม/หน้า/เวิร์กโฟลว์ทั่วไป · ภาษาเขียนกฎ · state machine ที่ผู้ใช้กำหนดเอง · ตาราง attribute–value (EAV) · schema แยกต่อ tenant · หลายสกุลเงิน · microservices / micro-frontend · event sourcing เต็มรูป (ตารางเก็บสถานะปัจจุบัน event เก็บประวัติ) · โมเดล "service order" ทั่วไปสำหรับธุรกิจที่ยังไม่มี

### 4.4 โมเดลข้อมูลหลัก

ทุกตารางธุรกิจมี `tenant_id` · เงินเป็นจำนวนเต็มหน่วยสตางค์ · ทุกการเขียน commit พร้อม `domain_event`

**4 บทบาทที่ทำให้ทั้ง 3 เฟสเป็นระบบเดียว**

| | เฟส 1 | เฟส 2 (ผู้ปล่อยเช่าจัดการเอง) | เฟส 3 (เราจัดการให้) |
|---|---|---|---|
| เจ้าของ `owner_org_id` | เรา | ผู้ปล่อยเช่า | ผู้ปล่อยเช่า |
| ผู้ดำเนินการ `operator_org_id` | เรา | ผู้ปล่อยเช่า | เรา |
| ที่เก็บ `custody_location_id` | ร้านเรา | บ้านผู้ปล่อยเช่า | คลังเรา |
| คู่สัญญารับเงิน `merchant_of_record_org_id` | เรา | ผู้ปล่อยเช่า (ผ่าน split settlement) หรือเรา (ช่วง pilot) | เรา |
| ผู้ตรวจของออก | พนักงาน | ผู้ปล่อยเช่า | พนักงาน |
| ผู้ตรวจของเข้า | พนักงาน | ผู้ปล่อยเช่า (+ ผู้เช่าตอนรับของ) | พนักงาน |
| ฐานอ้างอิงสภาพ | รายงาน check-in ครั้งก่อน | วิดีโอก่อนส่งของผู้ปล่อยเช่า | รายงาน intake ที่ผู้ปล่อยเช่าเซ็น |
| ผู้ตัดสินข้อพิพาท | ร้าน | แพลตฟอร์ม | แพลตฟอร์ม (และรับผิดเองในฐานะผู้รับฝาก) |

**เอนทิตีหลัก**

| เอนทิตี | ฟิลด์สำคัญ |
|---|---|
| `organization` | ประเภท (PLATFORM / SHOP / LENDER) สถานะ — เจ้าของชุดทุกรายเป็นองค์กร แม้เป็นคนเดียว; ผู้ใช้ถือบทบาทต่อองค์กร (ไม่มี admin flag ส่วนกลาง) |
| `party`, `identity_verification`, `trust_profile`, `blocklist_entry` | เบอร์โทร line_user_id; วิธีตรวจ ผล เลขบัตรเข้ารหัส keyed hash ความยินยอม วันหมดอายุ; ระดับและตัวนับ; ตัวระบุแบบ hash + เหตุผล |
| `category`, `product` | schema คุณสมบัติ แม่แบบเช็กลิสต์ ช่วงกันชน; ชื่อ ไซซ์ สี รูป |
| `unit` | ซีเรียล รหัส QR **4 บทบาท** โหมด (OWN / LENDER_MANAGED / PLATFORM_MANAGED) มูลค่าที่ตกลง กฎค่าเสื่อม ต้นทุน เกรด จำนวนครั้งเช่า น้ำหนัก ขนาด ชิ้นส่วน สถานะ `custody_holder` |
| `unit_fingerprint` (เข้ารหัส) | ตำแหน่งเครื่องหมายลับ รูปมาโคร |
| `pricing_rule`, `policy_profile`, `fee_schedule`, `checklist_template` | ดู 4.3 |
| `booking`, `booking_item` | ผู้เช่า merchant of record สถานะ วันที่ วิธีรับ–คืน snapshot ราคาและความเสี่ยง การยอมรับสัญญา; ผูกกับ unit จริงให้ช้าที่สุด |
| `availability_block` | unit ช่วงเวลา เหตุผล (BOOKING / BUFFER / MAINTENANCE / HOLD) — **exclusion constraint ของ Postgres ห้ามช่วงเวลาทับกัน ฐานข้อมูลจึงกันจองซ้อนเอง** |
| `custody_transfer` | unit ชนิด (CHECK_OUT / CHECK_IN / INTAKE / RETURN_TO_OWNER) จากใคร ถึงใคร วิธี (COUNTER / COURIER / MEETUP) การตรวจ การขนส่ง ลายเซ็นทั้งสองฝ่าย |
| `inspection`, `condition_finding`, `media_asset` | เวอร์ชันแม่แบบ ผู้ตรวจ (พนักงาน/ผู้ปล่อยเช่า/ผู้เช่า) เกรด ผู้รับทราบ; ประเภท ตำแหน่ง ความรุนแรง ที่มา ค่าใช้จ่าย; ไฟล์ SHA-256 เวลาเซิร์ฟเวอร์ ผู้อัปโหลด |
| `claim` | ผู้เรียกร้อง ผู้ถูกเรียกร้อง จำนวนเงิน กำหนดเวลา คำตัดสิน — มีตั้งแต่เฟส 1 แม้ร้านเป็นผู้ตัดสินฝ่ายเดียว |
| `shipment` | ขา ผู้ขนส่ง เลขพัสดุ มูลค่าที่แจ้ง น้ำหนัก เลขซีล เวลาสแกน |
| `payment`, `deposit`, `refund`, `ledger_entry` | อ้างอิงผู้ให้บริการ จำนวนเงิน idempotency key สิ่งที่ถูกจ่าย; สถานะมัดจำ; บัญชีรับคืน หลักฐาน กำหนดเวลา; บัญชีคู่: รายได้ค่าเช่า หนี้สินมัดจำ ค่าธรรมเนียม เจ้าหนี้ผู้ปล่อยเช่า คอมมิชชัน ภาษีหัก ณ ที่จ่าย |
| `deadline`, `task` | งานตามเวลาที่ขับกระดาน "วันนี้" และ playbook |
| `domain_event`, `audit_log` | เพิ่มได้อย่างเดียว เพิกถอนสิทธิ์ UPDATE/DELETE |

**State machine ของชุด (unit)**

```
INTAKE → AVAILABLE → RESERVED → OUT → RECEIVED → INSPECTING → CLEANING → (REPAIR) → AVAILABLE
ทางออกข้าง: HOLD_DISPUTE · OVERDUE · LOST · RETIRED · RETURNED_TO_OWNER
```

การขนส่งไม่ใช่สถานะของชุด — ใช้ `custody_holder` (ร้าน/ขนส่ง/ผู้เช่า/ร้านซัก/เจ้าของ) และระเบียน `shipment` แทน

**State machine ของการจอง (booking)**

```
HOLD (15 นาที) → CONFIRMED → READY → OUT → DELIVERED → ACTIVE → RETURN_DUE → RETURNING → RETURNED → INSPECTED → CLOSED
สาขา: DELIVERED → ISSUE_REPORTED · RETURN_DUE → OVERDUE → NON_RETURN
      INSPECTED → CLAIM_OPEN → RESOLVED → CLOSED · CANCELLED · EXPIRED
```

เงื่อนไขผ่านด่าน: **CONFIRMED** ต้องมีการรับเงินที่ยืนยันแล้ว มัดจำสถานะ HELD ยอมรับสัญญา และผ่านเกณฑ์ความเสี่ยง · **READY** ต้องตรวจขาออกครบ · **OUT/ACTIVE** ต้องมีการรับทราบจากผู้รับ (รับที่ร้าน) หรือสแกนของขนส่ง · **CLOSED** ต้องมีสถานะมัดจำขั้นสุดท้ายและสมุดบัญชีสมดุล

**สถานะมัดจำ:** `REQUIRED → HELD → RELEASING → REFUNDED | PARTLY_APPLIED | FORFEITED`

### 4.5 จากเว็บสู่แอป

| ขั้น | อะไร | เมื่อไร |
|---|---|---|
| 0 | เว็บ responsive; พนักงานติดตั้งเป็น PWA; ผู้เช่าเปิดใน LINE (LIFF / LINE MINI App) จาก rich menu: เลือกชุด · การจองของฉัน · คืนชุด · แชต | เฟส 1 |
| 1 | แอปพนักงาน (ห่อหน้าจอตรวจสภาพด้วย Capacitor) — งานกล้องหนักและต้องทนเน็ตหลุดคือจุดที่ native ช่วยได้มากที่สุด | เมื่ออัปโหลดหลักฐานล้มเหลว >2% หรือหน้าร้านต้องทำงานออฟไลน์ |
| 2 | แอปลูกค้า (Expo / React Native) ใช้ `packages/domain` + `api-client` ซ้ำ เขียนใหม่เฉพาะหน้าจอ | เมื่อลูกค้าเช่าซ้ำถึงราว 1 ใน 3 ของการจอง |

ข้อควรรู้: LINE เป็น "ช่องทาง" ไม่ใช่ "แพลตฟอร์ม" — เว็บต้องใช้ได้ในเบราว์เซอร์ทั่วไป (ลูกค้ามาจาก IG / TikTok / Google ด้วย) และบัญชีต้องผูกเบอร์โทรที่ยืนยันแล้ว · **ต้องทดสอบการถ่าย/อัปโหลดวิดีโอในเบราว์เซอร์ของ LINE บน iOS ตั้งแต่สัปดาห์แรก** (ใช้กล้องของเครื่องผ่าน file input; ถ้าไม่เสถียรให้เด้งไปเปิดในเบราว์เซอร์ของเครื่อง) · การเช่าของจับต้องได้ไม่ต้องใช้ in-app purchase ของ Apple (ต้องยืนยันกับ guideline ล่าสุดตอนส่งแอป)

### 4.6 ความปลอดภัยและ PDPA

- เข้ารหัสเลขบัตรและรูปบัตรในระดับแอปด้วยกุญแจที่มีระบบจัดการ; เก็บ keyed hash สำหรับตรวจซ้ำ/บัญชีเฝ้าระวัง
- พนักงาน: MFA สิทธิ์เท่าที่จำเป็น บันทึกทุกครั้งที่ดูข้อมูลตัวตน ลิงก์ไฟล์แบบมีอายุสั้น
- ประกาศความเป็นส่วนตัว · ฐานสัญญา/ประโยชน์โดยชอบสำหรับ KYC และหลักฐาน · ความยินยอมแยกสำหรับการตลาด · ความยินยอมโดยชัดแจ้งสำหรับการเทียบใบหน้า · ขั้นตอนคำขอของเจ้าของข้อมูล (ตอบภายใน 30 วัน) · ขั้นตอนแจ้งเหตุละเมิด (72 ชม.) · งานลบข้อมูลตามอายุ
- ข้อมูลอยู่สิงคโปร์ → ต้องมีข้อความเรื่องการส่งข้อมูลข้ามประเทศในประกาศ (ถ้าทนายให้เก็บในไทย ย้ายไป Postgres ในกรุงเทพฯ ได้)

## 5. เฟส 2 — เปิดให้คนอื่นมาปล่อยเช่า (Marketplace)

### 5.1 สิ่งที่เปลี่ยน

บนชุดของผู้ปล่อยเช่า: เจ้าของและผู้ดำเนินการคือองค์กรของผู้ปล่อยเช่า ที่เก็บคือที่อยู่ของเขา แพลตฟอร์มเป็นตัวกลางที่กำหนดสัญญามาตรฐาน ยืนยันตัวตน สั่งการชำระเงิน หักมัดจำ และตัดสินข้อพิพาทชั้นแรก

**ภัยใหม่:** ประกาศปลอม · ของก๊อป · ผู้ปล่อยเช่าเคลมเท็จใส่ผู้เช่า · พากันไปตกลงนอกแพลตฟอร์ม

### 5.2 การปล่อยของ การรับคืน และการเช็คสภาพ — ทั้งสองฝั่ง

ใช้เครื่องมือตรวจสภาพตัวเดิม โดยผู้ตรวจเป็นผู้ปล่อยเช่าหรือผู้เช่า

| ขั้น | ใคร | ภายในเมื่อไร | ถ้าไม่ทำ |
|---|---|---|---|
| หลักฐานขาออก (ชุดรูป + วิดีโอ) | ผู้ปล่อยเช่า | 24 ชม. ก่อนส่ง | เคลมผู้เช่าไม่ได้ |
| ตรวจรับ + วิดีโอแกะกล่อง | ผู้เช่า | 24 ชม. หลังได้รับ | เงียบ = ยอมรับสภาพ |
| วิดีโอแพ็กตอนส่งคืน | ผู้เช่า | ก่อนส่งคืน | โต้แย้งเคลมไม่ได้ |
| ตรวจรับคืน + วิดีโอแกะกล่อง | ผู้ปล่อยเช่า | 48 ชม. หลังได้รับ | เงียบ = ปกติ → ปิดอัตโนมัติ ปล่อยมัดจำ |

- **ช่องทางเริ่มต้น: ขนส่ง/แมสเซนเจอร์ที่สร้างรายการผ่านแพลตฟอร์มเท่านั้น** เพราะเลขติดตามคือบันทึกการถือครองที่เป็นกลาง การส่งนอกแพลตฟอร์มทำให้หมดความคุ้มครอง
- **นัดรับตัวต่อตัว** (เพิ่มเมื่อมีความต้องการ): ผู้ปล่อยเช่าแสดง QR ของการจอง → ผู้เช่าสแกน → ถ่ายรูปร่วมกัน → ทั้งคู่กดยืนยัน; **ห้ามส่งมอบก่อนแพลตฟอร์มแสดงว่า "จ่ายแล้วและยืนยันตัวตนแล้ว"**
- **ชุด Band C ในเฟส 2:** ยังไม่เปิดให้ส่งพัสดุ — ใช้ได้เฉพาะการนัดรับตัวต่อตัวแบบยืนยันสองฝ่าย การให้ชุดเดินทางผ่านจุดกลางของแพลตฟอร์มทำให้แพลตฟอร์มกลายเป็นผู้รับฝาก จึงเปิดได้เมื่อผ่านเงื่อนไขประกันและสัญญาของเฟส 3 แล้ว (7.3)
- ชุดของผู้ปล่อยเช่าทุกตัวได้ **ชุดป้ายของแพลตฟอร์ม** (QR ซีเรียล + ถุงกันแกะมีเลขกำกับ) และมีบันทึก intake ก่อนเช่าครั้งแรก; เลขซีลต้องเห็นในคลิปของทั้งสองฝ่าย
- **มูลค่าชุดประกาศตอนลงประกาศ แก้หลังเกิดความสูญเสียไม่ได้ และมูลค่าที่แพลตฟอร์มใช้คือค่าที่ต่ำกว่าระหว่างมูลค่าที่ประกาศกับราคาซื้อที่มีหลักฐาน** — ไม่มีหลักฐานการซื้อ ให้ใช้เพดานตามตารางของแพลตฟอร์มสำหรับชุดไม่มียี่ห้อ
- **หลักฐานขาออกของผู้ปล่อยเช่าต้องครบทุกมุมที่ระบบบังคับ** (รวมรูดซิปให้ดู ใต้วงแขน ชายกระโปรง) — เคลมบริเวณที่ไม่ปรากฏในหลักฐานขาออกจะถูกปฏิเสธ
- **ห้ามจองเมื่อผู้เช่ากับผู้ปล่อยเช่าเชื่อมโยงกัน** (อุปกรณ์ ที่อยู่ บัญชีธนาคาร ผู้จ่ายเงิน หรือเบอร์โทรเดียวกัน)

### 5.3 ข้อพิพาท

ใช้แบบฟอร์มมีโครงสร้าง ไม่ใช่แชตอิสระ → คู่กรณีคุยกันเอง 24 ชม. → แพลตฟอร์มเข้ามาที่ 72 ชม. → ฝ่ายถูกเรียกร้องมี 48 ชม. ตอบ → แพลตฟอร์มตัดสินภายใน 7 วัน จากหลักฐานในแอปของทั้งสองฝ่ายและตารางค่าเสียหายที่ประกาศ คำตัดสินเป็นที่สุดตามข้อตกลง ค่าเสียหายไม่เกินมูลค่าชุดหักค่าเสื่อม

กันผู้ปล่อยเช่าเคลมเท็จ: ตำหนิที่ถูกเรียกเก็บแล้วจะติดอยู่กับชุดเป็น "ตำหนิเดิม" จนกว่าจะมีใบเสร็จซ่อมและหลักฐานชุดใหม่ — เคลมประเภทและตำแหน่งเดิมซ้ำไม่ได้ · ค่าซ่อมจ่ายตามใบเสร็จ · ผู้ปล่อยเช่าที่เคลมเกินเกณฑ์ (เช่น 15% ของการเช่า) ถูกพักเพื่อทบทวน

### 5.4 การควบคุมคุณภาพและการรั่วออกนอกแพลตฟอร์ม

- ผู้ปล่อยเช่าผ่าน e-KYC และบัญชีธนาคารชื่อตรงเหมือนผู้เช่า
- ประกาศต้องผ่านการอนุมัติ มีมาตรฐานรูป เกรดสภาพ; ชุดมูลค่า >10,000 บาทต้องมีหลักฐานการซื้อ; ห้ามของเลียนแบบ; ถอดประกาศเมื่อคะแนนต่ำกว่าเกณฑ์
- ปิดบังช่องทางติดต่อจนกว่าจะจอง; ตรวจจับเบอร์โทร/LINE ID ในข้อความ; คุณค่าที่มีเฉพาะบนแพลตฟอร์ม (จัดการมัดจำ ความคุ้มครอง ตัวตนที่ยืนยันแล้ว ปฏิทิน รีวิว); ลดคอมมิชชันให้คู่ผู้ปล่อยเช่า–ผู้เช่าที่กลับมาใช้ซ้ำ

### 5.5 เงิน — ส่วนที่ไม่แน่นอนที่สุดของแผน

**ปัญหา:** การรับเงินจากผู้เช่าแทนผู้ปล่อยเช่าแล้วจ่ายต่อ น่าจะเข้าข่าย "บริการรับชำระเงินแทน" ที่ต้องได้รับอนุญาตตาม พ.ร.บ.ระบบการชำระเงิน พ.ศ. 2560 (ทุนจดทะเบียนขั้นต่ำหลักสิบล้านบาท) — ขอบเขตข้อยกเว้นยังไม่ได้ยืนยัน และจากการค้น: เอกสารของ Opn ระบุว่าไม่รับธุรกิจ marketplace, Stripe Connect มีข้อจำกัดในไทย, Xendit ทำการตลาดผลิตภัณฑ์ split payment ในไทยแต่ยังไม่ได้ยืนยันเงื่อนไข

**สองโครงสร้างที่ปลอดภัย**

| | A. ตัวกลาง + split settlement ของ PSP ที่มีใบอนุญาต | B. แพลตฟอร์มเป็นคู่สัญญารับเงิน (merchant of record) |
|---|---|---|
| เงิน | PSP ถือเงินจนปิดช่วงรับคืนโดยไม่มีเคลม แล้วจ่ายส่วนของผู้ปล่อยเช่าและค่าธรรมเนียมแพลตฟอร์มแยกกัน **เงินของผู้ปล่อยเช่าไม่เข้าบัญชีแพลตฟอร์ม** | แพลตฟอร์มให้เช่าในนามตัวเอง จ่ายส่วนแบ่งรายได้ให้ผู้ปล่อยเช่าเป็นเจ้าหนี้การค้า |
| ข้อดี | VAT คิดบนค่าธรรมเนียมเท่านั้น; ความรับผิดในฐานะผู้ให้เช่าอยู่ที่ผู้ปล่อยเช่า | ใช้ราง payment ของเฟส 1 ได้เลย ไม่มีคำถามเรื่องใบอนุญาต |
| ข้อเสีย | ต้องหา PSP ที่จ่ายให้บุคคลธรรมดาและหน่วงเวลาปล่อยเงินได้ | VAT บนค่าเช่าเต็มจำนวน; แพลตฟอร์มรับความรับผิดของผู้ให้เช่า; ต้องหักภาษี ณ ที่จ่าย |

**แนวทางที่แนะนำ:** pilot ปิดกับผู้ปล่อยเช่าที่เชิญ 10–20 ราย ด้วยโครงสร้าง B (ถ้าทนายยืนยัน) → ก่อนเปิดรับสมัครทั่วไป ย้ายไปโครงสร้าง A เมื่อมี PSP ยืนยันเป็นลายลักษณ์อักษร — `merchant_of_record_org_id` เป็นฟิลด์บนการจอง การสลับจึงเป็นเรื่องค่าตั้งค่าและสัญญา ไม่ใช่การรื้อระบบ **ห้ามมีเงินของผู้ปล่อยเช่าเคลื่อนไหวจนกว่าทนายด้านการชำระเงินจะให้ความเห็นเป็นลายลักษณ์อักษร**

**อัตราเริ่มต้น (ค่าตั้งค่า)**
- คอมมิชชันจากผู้ปล่อยเช่า 15–20% (10% ช่วงเปิดตัว) · ค่าบริการผู้เช่า 5–8% รวมอยู่ในราคาที่แสดง (ผู้เช่าไทยอ่อนไหวกับค่าธรรมเนียมแฝง)
- **ไม่คืนชุดเกินมัดจำ:** ผู้ปล่อยเช่ารับภาระ (มัดจำที่ยึดได้เป็นของผู้ปล่อยเช่า) แพลตฟอร์มส่ง evidence pack ให้ และจ่ายเงินช่วยเหลือแบบมีเพดาน (เช่น ค่าที่ต่ำกว่าระหว่าง 50% ของมูลค่าหักค่าเสื่อม กับ 5,000 บาท) **เฉพาะเมื่อครบทุกข้อ:** ผู้ปล่อยเช่าแจ้งความร้องทุกข์แล้วและอัปโหลดใบรับแจ้งความ · มูลค่าที่ใช้คือค่าที่ต่ำกว่าระหว่างที่ประกาศกับราคาซื้อที่มีหลักฐาน · ผู้ปล่อยเช่ามีการเช่าที่จบเรียบร้อย ≥3 ครั้งและอยู่บนแพลตฟอร์ม ≥60 วัน · คู่กรณีไม่เชื่อมโยงกัน · ไม่เกิน 1 ครั้งต่อผู้ปล่อยเช่าต่อ 12 เดือน · จ่ายไม่ก่อน D+45 — เงื่อนไขเหล่านี้กันการลงประกาศชุดราคาเกินจริงแล้วให้พวกเดียวกันเช่าไปไม่คืน
- **ค่า "ยกเว้นความเสียหายเล็กน้อย" (damage waiver) ยังไม่เปิดในช่วง pilot** — ผลิตภัณฑ์นี้ทำให้ผู้เช่าไม่มีเหตุโต้แย้งเคลม จึงเปิดช่องให้ผู้ปล่อยเช่าเบิกเงินจากแพลตฟอร์มได้ง่าย ถ้าจะเปิดภายหลังต้องมี: แพลตฟอร์มตรวจทุกเคลมเทียบกับหลักฐานขาออก (ไม่อนุมัติจากความเงียบ) · จ่ายตามใบเสร็จซ่อมหรือจ่ายตรงให้ร้านซ่อมที่แพลตฟอร์มเลือก · ผู้เช่ารับส่วนแรกเอง (เช่น 300 บาทแรก) · เพดานต่อคู่ผู้ปล่อยเช่า–ผู้เช่า และต่อผู้ปล่อยเช่าต่อไตรมาส · เรียกว่าการสละสิทธิ์เรียกร้อง ระบุชัดว่าไม่ใช่ประกันภัย (เสี่ยงถูกมองเป็นธุรกิจประกันวินาศภัยโดยไม่มีใบอนุญาต — ให้ทนายตรวจ)

### 5.6 สิ่งที่เฟส 1 ต้องมีไว้แล้ว

1. `tenant_id` ทุกตาราง และ 4 บทบาทถูกกรอกค่า (เป็นองค์กรของเราทั้งหมด)
2. เครื่องมือตรวจสภาพที่ผู้ตรวจเป็น "คู่กรณีฝ่ายใดก็ได้" พร้อมการรับทราบสองฝ่าย — ไม่ hard-code คำว่า "พนักงาน"
3. สิทธิ์ตามการเป็นสมาชิกองค์กร; สัญญามีเวอร์ชันต่อองค์กร
4. สมุดบัญชีมีบัญชี "เจ้าหนี้เจ้าของชุด" และตารางค่าธรรมเนียม 0%
5. ระเบียน `claim` พร้อมกำหนดเวลา
6. มูลค่าที่ตกลงต่อชุด และการยืนยันตัวตนที่ใช้ได้กับคู่กรณีทุกประเภท
7. ทุกฟังก์ชันอยู่หลัง API — หน้าจอผู้ปล่อยเช่าเป็นแค่ UI ใหม่บน endpoint เดิม

## 6. เฟส 3 — เราจัดการชุดให้ (Managed / ฝากเช่า)

### 6.1 รับชุดเข้า (intake)

1. เกณฑ์รับ: มูลค่าขายปลีก ≥3,000 บาท สภาพเกรด C ขึ้นไป ระยะฝากขั้นต่ำ 3–6 เดือน
2. พนักงานตรวจเต็มรูปแบบ: เกรด ขนาด น้ำหนัก ลายนิ้วมือชุด ชิ้นส่วน วิธีซัก แล้วติดป้ายและเครื่องหมายลับ
3. **แพลตฟอร์มเป็นผู้กำหนดมูลค่า ไม่ใช่ผู้ปล่อยเช่า:** ค่าที่ต่ำกว่าระหว่างราคาซื้อที่มีหลักฐาน กับตารางของแพลตฟอร์มสำหรับชุดเทียบเท่าที่ไม่มียี่ห้อ คูณตัวคูณตามสภาพ — มูลค่าแบบมียี่ห้อใช้ได้เมื่อมีหลักฐานการซื้อเท่านั้น พร้อมกฎค่าเสื่อม (เช่น −5% ต่อการเช่า และผูกกับเกรดสภาพตามหัวข้อ 3.3)
4. **ผู้ปล่อยเช่าเซ็นรายงาน intake และสัญญาฝากเช่าทางอิเล็กทรอนิกส์** — นี่คือฐานอ้างอิงของทุกเคลมในอนาคต รวมถึงเคลมที่มีต่อแพลตฟอร์มเอง
5. ในระบบ: `custody_transfer` ชนิด INTAKE; ผู้ดำเนินการและที่เก็บเปลี่ยนเป็นแพลตฟอร์ม; โหมดเป็น PLATFORM_MANAGED

### 6.2 การเก็บรักษาและความรับผิด

- แพลตฟอร์มเป็นผู้รับฝากโดยมีบำเหน็จ ต้องใช้ความระมัดระวังและฝีมือในระดับวิชาชีพ (ป.พ.พ. ม.659) และถ้าใช้ทรัพย์เกินกว่าที่เจ้าของอนุญาต ต้องรับผิดแม้เหตุสุดวิสัย (ม.660) → **สัญญาต้องอนุญาตเป็นลายลักษณ์อักษรให้: ปล่อยเช่า ซัก ซ่อมเล็กน้อย ส่งผ่านขนส่ง**
- มาตรฐานคลัง: ห้องเก็บล็อกได้ กล้องวงจรปิด ควบคุมความชื้นและแมลง รหัสราว/ช่อง สแกนทุกการเคลื่อนย้าย นับรอบทุกสัปดาห์ นับเต็มทุกเดือน ตัดจำหน่ายหรือคืนเจ้าของต้องใช้ 2 คน; UHF RFID เมื่อเกินราว 500–1,000 ชุด
- **ประกันทรัพย์สินของผู้อื่นที่อยู่ในความดูแล ต้องมีผลก่อนรับชุดแรก — ไม่มีประกัน ไม่เปิดเฟส 3**

**ใครรับความสูญเสียแบบไหน**

| เหตุ | ผู้รับภาระ |
|---|---|
| สึกหรอตามปกติ ผ้าเสื่อมตามอายุ | ผู้ปล่อยเช่า |
| ผู้เช่าทำเสียหาย | ผู้เช่า; ส่วนที่เก็บไม่ได้ของความเสียหายที่ซ่อมได้ แพลตฟอร์มรับ |
| ผู้เช่าไม่คืน หรือหาย/เสียหายระหว่างอยู่ในคลังหรือขนส่ง | แพลตฟอร์มจ่ายมูลค่าหักค่าเสื่อม **ภายในเพดานต่อชุดและเพดานต่อผู้ปล่อยเช่าต่อปีที่ระบุในสัญญา** แล้วไปไล่เบี้ยจากผู้เช่า ขนส่ง หรือประกัน — กรณีผู้เช่าไม่คืน จ่ายหลังแจ้งความร้องทุกข์แล้ว (D+30) |

**กันการสมรู้กันเบิกเงิน** (ผู้ปล่อยเช่าฝากชุดปลอมหรือชุดถูกในมูลค่าสูง แล้วให้พวกเดียวกันเช่าไปไม่คืน): มูลค่ากำหนดโดยแพลตฟอร์มตามข้อ 6.1 · ห้ามจองเมื่อผู้เช่ากับผู้ปล่อยเช่าเชื่อมโยงกัน · ความสูญเสียที่เกิดใน 3 การเช่าแรกของชุดต้องให้คนตรวจ · การนับสต็อกทำโดยคนที่ไม่ใช่ผู้ดูแลคลังประจำวัน และสุ่มตรวจด้วยลายนิ้วมือชุด

**ก่อนรับชุดแรก ขอคำตอบเป็นลายลักษณ์อักษรจากบริษัทประกันแยกตามเหตุ** (ผู้เช่าไม่คืน / ระหว่างขนส่ง / ในคลัง) — กรมธรรม์ทรัพย์สินในความดูแลมักไม่คุ้มครองกรณีส่งมอบให้ลูกค้าโดยสมัครใจแล้วลูกค้าไม่คืน (ยังไม่ได้ยืนยัน) เหตุใดที่ประกันไม่คุ้มครอง ให้จำกัดความรับผิดตามสัญญาไว้ที่เพดาน

### 6.3 ออกจากระบบ

ปลดระวางเมื่อเกรด X หรือเมื่อผู้ปล่อยเช่าแจ้ง (ภายใต้การจองที่มีอยู่) · คืนเจ้าของด้วย `custody_transfer` ชนิด RETURN_TO_OWNER ที่มีการตรวจและลายเซ็นเหมือนตอนรับเข้า · สัญญามีข้อกำหนดของที่ไม่มารับคืน และสิทธิยึดหน่วงเมื่อมีค่าบริการค้างชำระ (ม.670)

### 6.4 เรต 2 ระดับ

แพลตฟอร์มเป็นคู่สัญญารับเงิน (merchant of record) และจ่ายส่วนแบ่งรายได้ให้ผู้ปล่อยเช่า

| | จัดการเอง (เฟส 2) | เราจัดการให้ (เฟส 3) |
|---|---|---|
| ผู้ปล่อยเช่าได้ | 80–85% ของค่าเช่า | 50–60% ของค่าเช่า |
| แพลตฟอร์มได้ | 15–20% + ค่าบริการผู้เช่า 5–8% | 40–50% + ค่าบริการผู้เช่า |
| ถ่ายรูป เก็บ แพ็ก ตรวจ ซักตามปกติ | ผู้ปล่อยเช่า | แพลตฟอร์ม (จากส่วนแบ่งของตัวเอง) |
| ค่าส่ง | ตามที่ตกลงกับผู้เช่า | ผู้เช่าจ่ายตามจริง |
| ระยะขั้นต่ำ | ไม่มี | 3–6 เดือน |
| ชุดที่ไม่ถูกเช่า 90 วัน | — | คืนเจ้าของ หรือคิดค่าเก็บ 30–50 บาท/เดือน |

**ตัวอย่าง** ชุดมูลค่า 6,000 บาท ค่าเช่า 900 บาท
- จัดการเอง (คอมมิชชัน 18% ค่าบริการผู้เช่า 8%): ผู้ปล่อยเช่าได้ 738 บาท · แพลตฟอร์มได้รวม 234 บาท (คอมมิชชัน 162 + ค่าบริการผู้เช่า 72) ก่อนหักค่ารับเงิน
- เราจัดการให้ (50%): ผู้ปล่อยเช่าได้ 450 บาท · แพลตฟอร์มได้ 522 บาท หักค่าซัก 150 แพ็ก 40 ค่ารับเงิน 25 สำรองความเสียหาย 30 → **เหลือ ~275 บาท** ซึ่งต้องแบกความรับผิดกรณีไม่คืนชุดด้วย จึงต้องติดตามอัตราความสูญเสียรายผู้ปล่อยเช่า

> อัตรา 40–50% มาจากการเทียบเคียง (ฝากขายมือสองเก็บ 30–60%; Style Lend ปี 2014 แบ่ง 70/30 เมื่อเจ้าของจัดการเอง และ 50/50 เมื่อแพลตฟอร์มจัดการ) **ไม่ใช่อัตราคู่แข่งที่ยืนยันได้** — ให้ใช้เป็นจุดเริ่มแล้วปรับจากรายงานกำไรต่อการเช่าต่อระดับ

### 6.5 รายงานสำหรับผู้ปล่อยเช่า

หน้าพอร์ทัลอ่านอย่างเดียว: สถานะและตำแหน่งของแต่ละชุด · การเช่า อัตราการใช้งาน รายได้ · ประวัติเกรดพร้อมสื่อจากการตรวจ · ใบแจ้งยอดต่อการเช่า (ยอดรวม คอมมิชชัน รายการหัก สุทธิ) · การจ่ายรายเดือน · หนังสือรับรองการหักภาษี ณ ที่จ่าย (50 ทวิ) เมื่อผู้จ่ายเป็นบริษัท (ค่าเช่า 5% ค่าบริการ 3% สำหรับยอดตั้งแต่ 1,000 บาท — ให้นักบัญชียืนยัน)

## 7. Roadmap

### 7.1 เฟส 1

| Milestone | ช่วง | เนื้องาน | เกณฑ์ผ่าน |
|---|---|---|---|
| **M0 Concierge** | สัปดาห์ 0–2 | ตัดสินใจข้อ 9 · ติดป้าย/ถ่ายรูป/ตั้งมูลค่า 20 ชุดแรก · ปล่อยเช่าจริงผ่าน LINE + สเปรดชีต + เช็กลิสต์กระดาษ · สมัคร gateway และ e-KYC · ให้ทนายเริ่มร่างสัญญา | ตรวจสภาพได้ <5 นาที/ครั้ง; มีการเช่าจริง 20 ครั้ง |
| **M1 ฐานระบบ** | สัปดาห์ 1–3 | monorepo · องค์กร/tenant · เข้าสู่ระบบ (OTP, LINE) · โครง API · event log · ค่าตั้งค่า · **ทดสอบอัปโหลดวิดีโอใน LINE บน iOS, Safari, Android Chrome** | วิดีโอ 30 วินาทีอัปโหลดผ่าน 4G ได้เสถียร |
| **M2 ทะเบียนชุด** | สัปดาห์ 3–5 | หมวด/ชุด/unit · พิมพ์ป้าย QR · การตรวจ intake · หน้าร้านแสดงแคตตาล็อก | ชุดเปิดตัวทุกตัวมีซีเรียล มูลค่า และหลักฐานตั้งต้น |
| **M3 จองและเงิน** | สัปดาห์ 5–8 | ปฏิทินว่าง · ฟังก์ชันราคา/มัดจำ/ความเสี่ยง · การจอง · ยอมรับสัญญา · รับเงิน · สมุดบัญชี · คิวคืนเงิน · ยืนยันตัวตน | คนแปลกหน้าจองและจ่ายเองได้; จองซ้อนไม่ได้แม้ทดสอบพร้อมกัน; สมุดบัญชีกระทบยอดกับเงินจริงได้ถึงสตางค์ |
| **M4 ปล่อย–รับของ** | สัปดาห์ 8–11 | check-out / check-in · การขนส่ง · ตัวจับเวลา · playbook ไม่คืนชุด · เคลม · evidence pack · แจ้งเตือน LINE · กระดาน "วันนี้" | ผู้ทดสอบภายนอกเช่าแบบส่งพัสดุได้ครบวงจร |
| **M5 รายงานและเปิดตัว** | สัปดาห์ 11–13 | dashboard · view รายงาน · PDPA · สัญญาที่ทนายตรวจแล้ว · จดทะเบียนพาณิชย์อิเล็กทรอนิกส์ (DBD) · soft launch | 10 การเช่าครบวงจรในระบบ |

**กติกาขั้นต่ำของช่วง M0** (ชุดจริงออกจากร้านก่อนระบบและสัญญาฉบับทนายจะพร้อม จึงต้องเข้มกว่าปกติ): รับที่ร้านเท่านั้น · ดูบัตรตัวจริงและถ่ายรูปตอนส่งมอบ · มัดจำตามตารางในหัวข้อ 3.3 · ยืนยันเงินเข้าจากแอปธนาคาร ไม่ใช่จากรูปสลิป · สัญญากระดาษหนึ่งหน้าที่ลงชื่อ ระบุมูลค่าชุดและวันคืน · ชุดทุกตัวติดป้ายและถ่ายรูปก่อนปล่อยครั้งแรก

**ถ้าต้องเร่งให้เหลือ 6–8 สัปดาห์ ให้ตัดตามลำดับนี้:** การส่งของทุกรูปแบบพร้อม e-KYC ของผู้ให้บริการ (เปิดเฉพาะรับที่ร้านและตรวจตัวตนที่เคาน์เตอร์ — สองอย่างนี้ต้องตัดคู่กัน เพราะไม่มี e-KYC ห้ามส่งของ) → LINE push อัตโนมัติ (พนักงานกดส่ง) → dashboard (ใช้ view + CSV) → LINE Login — **แต่ห้ามตัดรายการในหลักการข้อ 5 (หัวข้อ 2)**

**เกณฑ์จบเฟส 1 (ประมาณ 100 การเช่าที่ปิดแล้ว):** หลักฐานครบทั้งขาออกและขาเข้า ≥98% · คืนมัดจำภายใน 24 ชม. ≥95% · ไม่มีการจองซ้อน · รู้อัตราคืนช้า เสียหาย และสูญหายจริง · มี evidence pack อย่างน้อย 1 ชุดที่ทนายเห็นว่าพร้อมแจ้งความ · วัดอัตราหลุดที่ขั้น KYC/มัดจำแล้ว · กำไรส่วนเกินต่อการเช่าเป็นบวก · ตัวชี้วัดในหัวข้อ 3.6 ออกได้โดยไม่ใช้สเปรดชีต

### 7.2 เฟส 2

**เงื่อนไขก่อนเปิด:** จดทะเบียนบริษัทจำกัด · ความเห็นทนายเป็นลายลักษณ์อักษรเรื่อง พ.ร.บ.ระบบการชำระเงิน และโครงสร้าง A/B · คำยืนยันจาก PSP เรื่อง split settlement ให้บุคคลธรรมดา + หน่วงเวลาปล่อยเงิน (หรือการตัดสินใจเป็น merchant of record) · แจ้ง ETDA ตามกฎหมายแพลตฟอร์มดิจิทัล · สัญญามาตรฐานผู้ปล่อยเช่า–ผู้เช่า และข้อตกลงการใช้แพลตฟอร์ม · e-KYC อัตโนมัติ · แผน VAT

**Pilot:** ผู้ปล่อยเช่าที่เชิญ 10–20 ราย → **เกณฑ์จบ:** 100–300 การเช่าระหว่างบุคคล · ข้อพิพาท <5% และตัดสินทันกำหนดทุกเคส · จ่ายผู้ปล่อยเช่าตรงเวลา

### 7.3 เฟส 3

**เงื่อนไขก่อนเปิด:** สถานที่เก็บที่ผ่านมาตรฐานข้อ 6.2 · กรมธรรม์คุ้มครองทรัพย์สินของผู้อื่นมีผลแล้ว · สัญญาฝากเช่า · ขั้นตอนภาษีหัก ณ ที่จ่ายและเก็บเลขผู้เสียภาษีของผู้ปล่อยเช่า

**Pilot:** 5 ราย 50 ชุด 3 เดือน → **เกณฑ์จบ:** ผลนับสต็อกตรงกับระบบ 3 เดือนติด · ไม่มีความสูญเสียในความดูแลที่เอาคืนไม่ได้ · กำไรส่วนเกินต่อการเช่าแบบ managed เป็นบวกหลังหักความสูญเสีย

> **ข้อเสนอเรื่องลำดับ:** ในเชิงปฏิบัติการ เฟส 3 (ฝากเช่า) คือ "เฟส 1 ที่เจ้าของชุดเป็นคนอื่น" จึงเป็นก้าวที่เล็กกว่าเฟส 2 และไม่ติดปัญหาใบอนุญาตรับชำระเงินแทน ทางเลือกคือทำ pilot ฝากเช่าขนาดเล็กกับคนรู้จัก 3–5 ราย *ก่อนหรือคู่ขนานกับ* การเปิด marketplace — ค่าเริ่มต้นของแผนยังคงลำดับเดิมตามโจทย์ (ดูข้อ 9)
